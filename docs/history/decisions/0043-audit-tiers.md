# ADR 0043：审计按事件级别分级，访问类事件有界聚合

- 状态：已采纳
- 日期：2026-10-24
- 相关：需求 15.3、18.11、20.4、ADR 0039、ADR 0040、ADR 0042

## 背景

2026-10-23 那次故障里，审计记录总量 91,386 条，其中 91,328 条是 sync（99.94%），
真实业务事件只有 58 条，合计 12,916 字节。

这组数字说明两件事：

一是审计本身不需要很大。58 条业务事件摊到 41 小时约 34 条/天，按每条约 223 字节
算，一个用户一年约 3 MB。审计的体积问题从来不在"记业务事实"。

二是故障时那 8.4 万条噪声不是审计写多了，而是它把一个上游 bug 逐级放大：
对账每秒重发一轮，每轮记一条，每条 fsync，每 5 秒一次 commit。
最终 76,350 个 commit 把 `.git` 撑到 5.7G，写满 40G 系统盘，整机失联 65 分钟。

更根本的问题在于分类：把"传输"当成了"事实"。需求 15.3 要求审计覆盖"下发"，
但"这台设备又收到了同一份内容"属于传输过程，不是业务事实——它真正的来源是
SSOT 的那次 commit，本身可以从 commit 历史和设备状态推导出来。而它的频率由
bug 和网络决定，不由业务决定。这类事件一旦逐条落盘，审计就成了故障放大器。

ADR 0042 曾用"内容指纹 + 30 分钟静默期"降噪。这个方向对但不彻底：
故障后期内容每轮都在变（说明行被反复叠加），指纹全不同，降噪完全失效；
而且"忽略哪一行/哪个字段"的规则散落在调用点，容易再次漂移。

## 决策

### 一、按"信息量是否会被重复淹没"分三级，而不是按事件重要性平铺

- A 安全与不可逆：密钥写入/删除/明文查看/下发、设备登记/恢复/吊销/类型变更、
  根密钥加载与轮换、初始化、部署、回滚、本地改动覆盖。
- B 业务事实：资产写入/删除、项目与订阅变更、冷备结果。
- C 传输与访问：下发、客户端下载。

分界线不是"重不重要"，而是频率由谁决定：A 由人的操作决定，B 由 SSOT commit
决定，两者天然有界；C 由网络重连、长轮询超时乃至 bug 决定，可以无界。

因此限额只作用于 C。A 与 B 在任何高频下都逐条 fsync，绝不聚合、绝不因限额丢弃。
测试 `TestSecurityTierNeverSuppressed` / `TestFactTierNeverSuppressed` 锁住这条。

未知事件默认按 C 处理。新事件在证明自己低频之前先当成"可能刷屏"，
避免再出现一次"把高频事件当事实级而写满磁盘"。

### 二、C 类按 (事件, 设备, 来源地址, 对象) 每小时聚合，且有三重上限

- 单键上限 `MaxAccessRecordsPerHour = 20`：限制单台设备疯狂重发。
- 全局限额 `MaxAccessRecordsPerHourTotal = 400`：限制"换键刷屏"。
- 桶上限 `MaxAccessBuckets = 1024`：超出后新键折进溢出桶。

单键限额单独是不够的。下载端点是公网匿名接口，聚合键含 IP，而 IP 可随意轮换：
每换一个 IP 就是一个新桶，每个桶只用了 1 次额度，单键限额永远触发不了。
没有全局上限，这次改造就只是把"磁盘写满"换成"内存吃满"。
`TestGlobalLimitStopsKeyRotation` 专门覆盖这个场景。

三个上限都不丢事实：超出部分累计成一条带 `count` 的汇总记录，放行数 + 聚合数
恒等于请求数。"发生过一万次"这个量级信号必须留下，否则事后无法区分
"正常重连"和"对账失控"—这正是降噪要保住的东西。

聚合键刻意不含 sync 的 revision：它每次业务提交都会变，拿来当键会让桶无限增殖。
`TestSyncAuditIgnoresRevisionForBucketing` 锁住这条，它对应的正是旧指纹方案
失效的那个场景。

### 三、结算时机只有两个：小时切换与进程退出

`Flush` 只做 git 提交，不结算聚合计数。这是实现过程中踩到的坑：
最初让 `Flush` 每次都把 `suppressed` 结算成汇总，而冷备推送前会周期性 `Flush`，
于是在"每写一条就 Flush"的场景下，每条被抑制的记录都变成一条 `count=1` 的
汇总重新写回文件，聚合等于没做（实测 200 次下发仍落盘 200 条，上限是 20）。

正确的结算点：小时切换由 `Offer` 内部自动完成；进程退出由 `Log.Close` 完成。
`Flush` 是周期性调用的，不能承担结算职责。`TestFlushDoesNotResettleAggregates`
锁住这条。

### 四、审计失败必须让业务继续，但失败要可数

`writeEntry` 失败只累加 `Log.Dropped()`，不向上传播。这条与 `Server.record`
的既有取舍一致，但把"静默丢"改成"可数的丢"：审计有洞这件事必须能被管理面看见。

`TestAuditFailureDoesNotBreakBusiness` 用"堵死 events 目录"的方式验证：
审计完全写不进去时，资产写入仍然成功，且 `Dropped()` 增长。

## 影响

- 正常使用完全不受影响。一台设备一小时对账 10 次、偶尔下载客户端，
  远低于任何阈值，`TestNormalUsageUnaffected` 锁住这条。
- 失控场景下，单小时单设备的 sync 记录从"每秒一条"降到最多 21 条
  （20 条原始 + 1 条汇总）。
- 下载审计保留（需求 20.4 要求记入审计），但同样受限额约束，
  不会被一次爬取撑大审计仓库。
- 移除了 ADR 0042 的内容指纹降噪：它已被日志层的分级聚合取代。
  降噪规则集中在一处，不再散落在各调用点。

## 未采纳的方案

**把下载完全移出审计、只留监控指标**：需求 20.4 明确要求"访问记入审计日志"，
移出等于不满足验收。改为受限额约束地保留。

**C 类完全退出审计**：会丢掉"下发到过哪些设备"的取证能力，
而设备吊销后要能回答这个问题的需求（18.8、18.11）仍在。

**任何情况下都逐条记**：等于接受"审计可能再次拖垮服务"。
2026-10-23 已经证明这个代价不可接受。
