# 空哈希也必须记一条覆盖事件

## 背景

[0047](0047-multi-path-hash-compare.md) 修掉了多落点哈希只取最后一份的漏检缺陷：
一个条目同时落在 `.claude/`、`.codebuddy/`、`.codex/`、`.cursor/`、`.with/`
五个目录时，只要有一份与其它不同，代理就上报空哈希，请求云端完整补发。

修完当天发 v2.1.21 上线，随后做需求 5（离线降级）实测时踩到了连带缺陷：
本地改 `.cursor` 那份（路径列表第 4 个），40 秒内文件确实被覆盖回云端内容，
但服务端 `state/<device>.json` 的 `overrides` 里一条记录都没有。

## 问题

覆盖检测的判断是这样写的：

```go
if seen && cur.Hash != "" {
    if prev, ok := state.Files[f.File.ID]; ok && prev.Hash != cur.Hash {
        overrides = append(overrides, ...)
    }
}
```

`cur.Hash != ""` 这个前置条件来自「空哈希只可能是删除回执」的年代。但 0047
之后空哈希多了一个含义：这个条目有多份副本，代理保证不了它们的状态。两个
含义撞在一起，后果是：

- 覆盖照常发生（`files = append(files, f.File)` 在判断之外），文件被静默改回。
- 审计里没有任何痕迹。

这比完全不检测更糟。完全不检测至少还能看出「没生效」；现在是生效了但查不到
是谁、什么时候、改了哪一份，出问题时无从追溯。

## 决定

去掉 `cur.Hash != ""` 前置条件，只保留下面的 `prev.Hash != cur.Hash`：

```go
if seen {
    if prev, ok := state.Files[f.File.ID]; ok && prev.Hash != cur.Hash {
        overrides = append(overrides, ...)
    }
}
```

`prev.Hash` 是上一次落地回执记录的哈希，一定非空（空哈希的回执走的是删除分支，
会把条目从 `state.Files` 里删掉）。所以首次下发时 `prev` 不存在，不会误记；
之后任何形式的「与上次落地不一致」都会落一条记录，包括空哈希。

## 后果

- 覆盖记录从「只在代理报出具体哈希时才有」变成「只要发生覆盖就有」。
- `Override.Hash` 可能为空。管理面只展示条目、落点、时间，不展示哈希，
  所以展示层不受影响；将来若要按哈希去重或回溯，需要按「空 = 多副本不一致」
  理解，且不能拿它当改动指纹比对。
- 去重规则按哈希是否为空分两种：非空哈希按值判重（同一次改动只留一条），
  空哈希只在 2 秒窗口内判重（同一轮对账的重复判断）。空哈希的同一处本地改动
  跨轮次重复上报仍会各记一条，属刻意取舍——宁可多记，不能漏记。

## 备选方案

**让代理上报「哪一份不同」而不是空哈希。** 更精确，但要在协议里加字段、
代理要逐个落点算哈希再挑出差异项，改动面比这次修复大得多，且会破坏 0047
定下的「空哈希 = 保证不了」这条简单约定。当前需求只要求「知道被改过」，
不需要「知道改的是第几份」，不划算。

**在代理侧先自己覆盖，再上报新哈希。** 违反需求 6.1（代理不保存下发清单、
不做双向同步），也违反需求 5.2（本地落点只是只读缓存）。不做。

## 第二处根因：去重时的 map 零值陷阱

只去掉 `cur.Hash != ""` 还不够。改完发 v2.1.22 上线后重测，记录仍然不出现。
真正把记录吞掉的是 `AddOverrides` 的去重：

```go
last := make(map[string]string, len(st.Overrides))
for _, o := range st.Overrides {
    last[o.ID] = o.Hash
}
for _, o := range overrides {
    if last[o.ID] == o.Hash {   // ← 这里
        continue
    }
    ...
}
```

`last` 用 `o.ID` 建索引，取不存在的键返回零值 `""`。空哈希也正好是 `""`。
所以「这个条目从来没被记录过」和「这个条目记过一条空哈希」在比较时完全等价，
第一条空哈希覆盖必然被当成重复丢掉。非空哈希没有这个问题，因为零值 `""`
不可能等于一个真实的 sha256 值。

改成用 `ok` 判断存在性：

```go
if prev, ok := last[o.ID]; ok && prev == o.Hash {
    continue
}
```

## 第三处根因：空哈希不是改动指纹

修完前两处、发 v2.1.23 上线后，真机实测仍然复现：文件被覆盖回基线，`overrides`
条数不变。把状态文件按秒采样后看清了过程——`files` 的 `applied_at` 在往前推，
`overrides` 却停在更早的一条，说明覆盖走了完整下发路径、`AddOverrides` 也调到了，
是被判重丢掉的。

问题在 `ok` 判断只解决了「键存不存在」，没解决「值能不能当指纹」：

```go
last[o.ID] = lastSeen{hash: o.Hash, at: o.DetectedAt}
...
if prev, ok := last[o.ID]; ok && prev == o.Hash {
    continue
}
```

非空哈希是内容的指纹，值相同确实就是同一次改动。空哈希不是：代理报空哈希的
含义是「多落点里有一份与别的不同，我保证不了这条的状态」（0047），它对「改了
什么」「改了几次」一无所知。同一个条目被改十次，十次都报 `""`。按哈希值判重
等于认定「这个条目这辈子只会被改一次」，第二次及以后的覆盖全部静默丢弃。

这也解释了为什么前两处修完还不行：第一处修好让空哈希能进 `overrides` 的计算，
第二处修好让第一条能落库，而真机上一次验证往往已经是第二次以后的改动，正好
落在第三处的盲区里。

## 决定（第三处）

空哈希只按时间窗口去重，不按值判重：

```go
if seen {
    if o.Hash != "" {
        if prev.hash == o.Hash {
            continue        // 非空哈希：值相同即同一次改动
        }
    } else if prev.hash == "" && o.DetectedAt.Sub(prev.at) < emptyHashDedupWindow {
        continue            // 空哈希：只压掉同一轮对账内的重复判断
    }
}
```

`emptyHashDedupWindow` 取 2 秒。保留一个窗口是必要的：长轮询被唤醒后
`mSync` 会再算一次 `Sync`，同一件事在毫秒级内被判断两遍，不去重就会每次都
记两条。窗口取得很小是刻意的取舍——宁可多记一条，也不能把一次真实覆盖记成
没发生。审计的价值在于「事后能查到发生过什么」，多一条噪声只是难看，少一条
就失去了追溯能力。

## 三个根因的共同点

三处判断都写在「空哈希只可能是删除回执」的年代。删除回执的空哈希根本走不到
这些位置：删除的条目在 `RecordAck` 里就被从 `state.Files` 移除了，`want.Files`
里也不会再有它。所以这些空哈希分支在当时是死代码，写的时候不必想清楚语义。
0047 给空哈希赋予新含义后，死代码在三处同时变成活地雷，逐个才被发现。

教训是：给一个已有取值追加新语义时，要把它所有读取点都找出来重新审一遍，
不能只改产生它的地方。三处判断分散在两个文件、两层（渲染层比对与状态层去重），
只改一处就以为修完，是这个缺陷连修三版才干净的直接原因。

## 三处根因为什么同时存在

`cur.Hash != ""`、`last[o.ID] == o.Hash`、`prev == o.Hash` 都写在「空哈希只可能
是删除回执」的年代。删除回执的空哈希根本不会走到这三处：删除的条目在
`RecordAck` 里就被从 `state.Files` 移除了，`want.Files` 里也不会再有它。所以
这三个空哈希判断在当时都是死代码，写的时候不用想清楚它的语义。0047 给空哈希
赋予新含义后，死代码变成了活的地雷，而且三处都踩了。

## 验证

- `TestSyncRecordsOverrideWhenHashUnreported`：空哈希补发必须有覆盖记录，
  且记录带上代理上报的全部落点。旧实现下失败。
- `TestSyncFirstTimeEmptyHashIsNotOverride`：首次下发就报空哈希不该有记录，
  防止修复过头。
- `TestAddOverridesKeepsEmptyHash`：首次空哈希必须落库、重复的同样空哈希
  才去重、哈希变化要新增。实测把去重改回旧写法，这条立刻报
  「空哈希的首次覆盖必须记下来，实际 0 条」。
- `TestAddOverridesEmptyHashTwiceNotDeduplicated`：两次不同的改动都报空哈希时
  必须各记一条。实测把去重的时间窗口去掉并改回按值判重，这条立刻报
  「两次不同的改动都报空哈希时必须各记一条，实际 1 条」。
- `TestAddOverridesEmptyHashSameRoundDeduplicated`：同一轮对账内（毫秒级）
  的重复判断仍要去重，防止修复过头把一条改动记成两条。
- 真机实测（2026-10-26，v2.1.23）：五落点条目改 `.cursor` 那份，40 秒内五个
  落点全部覆盖回基线；服务端 `state/<device>.json` 的 `overrides` 首次出现
  该条目记录，`hash` 为空、`paths` 带全部五个落点。
