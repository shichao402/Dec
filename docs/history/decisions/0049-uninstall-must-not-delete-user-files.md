# 卸载不得删用户自己的文件

## 背景

需求 2.11 要求代理提供卸载命令，清理「所有由 Dec 管理的落点」。需求 6.4 要求
托管文件带一句说明「由 Dec 管理，本地修改会被覆盖」（实现见 [0041](0041-notice-rendered-by-server.md)）。

卸载有两条清理路径：

1. 向云端要一次核对清单（`Checks`），按清单里的绝对路径逐项删。这条是准的：
   云端记着的就是它下发的条目。
2. 兜底扫描：把每个宿主的 `skills/`、`rules/`、`env/` 目录整体扫一遍，把扫到的
   文件全删。用于「云端不知道某个条目的路径」的场景，比如项目被移出登记后留下的
   残留。

问题在第二条：`ScanManaged` 原本把目录下的**一切文件**都当成 Dec 写的。

## 问题

`skills/` 与 `rules/` 不是 Dec 独占的目录，是用户和 Dec 共用的：

- `~/.claude/skills/` 下既有 Dec 下发的 skill，也有用户自己写的 skill。
- `~/.cursor/rules/` 下既有 Dec 下发的规则，也有用户自己手写的 `.mdc`。

卸载时兜底扫描会把两者一起删掉。这是不可逆操作：用户自己写的规则、自己攒的
skill 没有任何备份，删掉就没了。

实测复现（2026-10-26，隔离 HOME）：在 `~/.claude/skills/` 下同时放一个 Dec 管理
的 skill 和一个用户自己的 skill，在 `~/.cursor/rules/` 下同时放一个 Dec 管理的
规则和一个用户手写的规则，执行 `dec-agent uninstall`，四个文件全被删除，
输出为「已删除 3 个落点」——用户那两个文件也算进了「落点」。

## 决定

兜底扫描按说明行判定归属，只删带 `notice.Text` 的文件：

```go
ours, err := managedByNotice(p)
if err != nil || !ours {
    return nil
}
out = append(out, p)
```

`managedByNotice` 只读文件开头 4KB 判断是否包含 `由 Dec 管理`，不整文件读入。

没有说明行不等于一定不是 Dec 写的：`.yaml`、`.env` 与含密钥文件按
[0041](0041-notice-rendered-by-server.md) 的规则不加说明行。这些条目由第一条
路径（云端核对清单里的绝对路径）清理，不依赖兜底扫描。两条路径的分工因此是：

- 知道确切路径的，按路径删，不看内容。
- 不知道路径的，只删带说明行的，宁可漏删也不误删。

## 后果

- 用户自己的 skill、规则在卸载后保留。
- 兜底扫描对 `.yaml` / `.env` 类条目无效，这类残留需要云端在线时通过核对清单
  清理。离线卸载会留下它们。这是刻意的取舍：漏删是可发现、可补救的（重装后
  再删一次），误删不可补救。
- 卸载后宿主目录下会留下空目录（`skills/dec-demo/` 这类）。不影响使用，
  暂不处理；将来若清理，必须同样只删空目录。

## 备选方案

**按命名前缀判定（`dec-` 前缀）。** 需求 6.3 对共享配置文件里的条目用了这个思路，
但落点文件名由云端条目的相对路径决定，用户完全可能把云端条目命名成 `my-rule.md`，
按前缀判会漏删。说明行才是 Dec 自己写下的、可控的标记。

**只走云端核对清单，去掉兜底扫描。** 会丢掉「项目被移出登记后的残留清理」这条
能力，那正是兜底扫描存在的理由。

## 验证

- `TestScanManagedKeepsUserFiles`：同目录下 Dec 管理的文件（含 front matter 之后
  带说明行的）必须被扫出，用户自己的 `.mdc` 与 `SKILL.md` 必须不被扫出。
  实测把实现改回「整目录一律删」，这条立刻报「只应扫出 Dec 写的 2 个文件，
  实际 4 个」。
- `TestScanManagedIgnoresMissingDir`：目录不存在时不报错，卸载能在没装宿主的
  机器上跑完。
- 真机实测（2026-10-26，隔离 HOME，修复后二进制）：Dec 管理 2 个文件、
  用户自有 2 个文件、`.env` 1 个，执行卸载后只剩用户自有 2 个与 `.env`，
  输出「已删除 2 个落点」。
