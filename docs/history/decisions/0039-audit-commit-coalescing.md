# 0039 审计提交按时间窗合并，冷备推送前冲写

## 背景

2026-10-23 22:01 起生产机（腾讯云轻量 `lhins-h50ld7m7`，香港，2 核 2G，40G 系统盘）
整机卡死：`ping` 通、CPU/磁盘监控仍有采样点，但 SSH 与 HTTPS 全部无响应，
本机 `dec-agent` 从 22:01 起每轮同步都超时，持续约 65 分钟。

重启后定位到根因：审计仓库 `.git` 已膨胀到 5.7G，系统盘使用率 84%。
`/var/lib/dec-cloud/audit` 有 76,350 个 commit，工作树只有 15M，
也就是说 5.7G 里几乎全是提交历史。

根因是审计的提交策略：每条记录一次 commit。一次 MCP 会话就能产生几万条记录，
每 2–3 秒一个 commit。git 的松散对象不会自动清理，go-git 写入也从不触发 `gc`。
盘写满后，写入路径全部阻塞在内核 I/O 上，连 sshd 的 fork 都无法完成——
表现出来就是"机器还活着，但什么都连不上"。

## 决策

1. **记录与提交解耦。** 记录仍然逐条 `fsync` 到工作树文件，这一步不变，
   它才是"进程崩溃不丢数据"的保证。commit 只负责把改动记进历史。
2. **提交按窗口合并。** 新增 `CommitWindow = 5s` 与 `CommitBatch = 200`：
   攒够 5 秒或 200 条才提交一次。同一段密集写入从"每条一个 commit"
   降到"一到几个 commit"。
3. **启动时补提交。** `Open` 里调一次 `commitPending`，
   把上次进程遗留的未提交改动补成 commit，不让它一直悬在工作树里。
4. **推送前冲写。** 新增 `Log.Flush()`，由冷备服务在推送审计仓库前调用。
   推送只看已提交内容，不冲就会漏掉最近几秒的审计。
5. **不在 backup 包直接依赖 audit 包。** 通过 `Options.FlushAudit func() error`
   回调注入，避免底层能力反向依赖上层。

## 为什么推翻原来的"单条即提交"

原注释的理由是"即使下一秒机器被砸了，也已经记下来了"。这个目标是对的，
但它把 commit 当成了持久化手段——而持久化其实在图前一步的 `fsync`。
真正被牺牲的是仓库体积：一次会话几万条记录，把盘写满，
最终结果不是"审计更安全"，而是**整台机器下线、审计也写不进去**。

用窗口换体积之后，两点都没丢：

- 进程崩溃：记录已 `fsync`，重启后 `Open` 补提交，一条不少（有测试锁住）。
- 机器断电：同上，损失上限是一个窗口内的未提交状态，记录本身仍在磁盘上。

## 被否方案

- **A. 只做 `git gc`，不改提交策略。** 治标。gc 只能回收历史，
  照原策略每天都会重新长回去，等于定时炸弹。
- **B. 审计不进 git，直接追加文件。** 会失去"按 commit 追溯变更"的能力，
  也不能再用冷备推送同一套机制。
- **C. 每条记录 commit 但定期自动 gc。** gc 在 5.7G 仓库上要跑很久且很吃内存，
  2G 小机器上跑 gc 本身就会把机器拖死——这次故障的直接触发点就是这种放大效应。
- **D. 加大系统盘。** 40G 已经是该规格上限，且掩盖问题而非解决。

## 运维影响

- 审计的 git 历史从"每条一个 commit"变成"每窗口一个 commit"。
  记录本身仍带秒级时间戳，按事件排查不受影响；只是不能再用
  `git log` 数条数——条数看文件行数。
- 冷备推送前多一次 `Flush`，正常情况下是一次空操作（工作树干净）。
- 事故处置记录：本次对生产机执行了 `git gc --prune=now`，
  `.git` 从 5.7G 降到 50M，磁盘使用率 84% → 69%。
  因机器已完全失联，先用腾讯云 API 重启（`RebootInstances`）恢复 SSH，
  再停服 gc、重启服务。
