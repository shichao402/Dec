# 0040 审计有自己的推送节奏，不再等"有人改内容"

## 背景

2026-10-23 修完审计仓库膨胀（见 [0039](0039-audit-commit-coalescing.md)）后，
第二天复查远端，发现审计远端一直停在重建历史时的归档提交 `d8df526`
（2026-10-23 17:30:51Z），而本地在这之后已经累积了大量 `审计 N 条` 的合并提交。

顺着推送触发链查下去，原因很直白：

- `Service.Trigger()` 的常规调用点只有一处——`cloudsvc.recordRevision`，
  且要求 `ok == true`。也就是说：**只有真正改了内容才推**。
- 审计里另外几条写入路径全部只 `Append`，不触发推送：
  `record() `（登记、恢复、密钥明文查看）、`recordSync()`（下发）、
  `recordLocalTLS()`（本机证书私钥下发）、`download.go` 与 `deploy.go` 的埋点。
- 剩下的路径只有 `dailyTick` 的 24 小时兜底。

于是出现一个很别扭的不对称：**冷备是新的，审计是旧的**。
一次 MCP 会话往往只读不写——查密钥、看资产、代理轮询下发——
这些恰恰是事后最需要追溯的动作，它们的审计却要等最长 24 小时才上远端。
真在这段时间里机器坏掉，冷备能把"现在是什么样"恢复出来，
但"谁在什么时候看过哪把密钥"这段记录一起没了。

`audit.go` 里那句注释"审计仓库自己也有一份推送节奏"，
当时指向的其实只有 24 小时兜底。这句话是对的，但那个节奏不对。

## 决策

1. **给审计一条独立周期。** 新增 `Options.AuditTick`，默认 30 分钟，
   到点只推审计仓库，不等 `Trigger`。
2. **周期推送不顺带推冷备。** `flush` 拆成 `flushBoth(ctx, withBackup bool)`；
   `auditTick` 走 `pushAuditOnly`，跳过冷备。冷备没变化，多推一次只是白跑一趟 fetch。
3. **暂停语义覆盖审计。** 部署期间 `Pause()` 同样拦住审计周期：
   部署中的操作可能随后被回滚，提前推上去会污染远端历史（需求 21.2）。
   `Resume()` 已有的 `Trigger` 会立刻补推一次。
4. **24 小时兜底保留。** 它防的是"进程重启导致某次触发漏掉"，与审计周期职责不同，
   不合并。

## 为什么最终改成按小时分片

把周期放宽到 30 分钟之后又测了一轮，仓库还是长得离谱：45 分钟里 `.git` 从 15M 涨到 82M，
松散对象 2650 个、内存被顶到可用 66MB（swap 2G 全满）。这说明问题不在频率，在文件粒度。

审计原有设计是"每天一个 jsonl 持续追加"。这个设计对纯文本归档没问题，
但放进 git 就完全变了性质：git 存的是文件全量快照，不是增量。
当天那个文件已经 9MB，于是**每一次提交都要重新存一遍这 9MB**。

分片后每个文件只覆盖一小时，提交只影响当前这一小时，历史小时不再重存。
单次提交的数据量与小时内的记录数成正比，与"这一天已经写了多少"无关。

`Read(day)` 同时兼容新的小时分片与旧的按天文件（`events/YYYY-MM/YYYY-MM-DD.jsonl`），
否则升级前的历史档案会变得读不出来。

## 为什么是 30 分钟（含一次真实翻车）

第一版取的是 5 分钟，理由是"上限要远离 24 小时"。上线当天就出了事，教训值得留在这里。

更直接的是内存。go-git 推送前要把松散对象重新打包，当时审计仓库累积了 1761 个
松散对象、52MB。2026-10-24 01:57:41，`dec-cloud` 的 anon-rss 涨到 754MB，
在 956MB 的机器上触发全局 OOM 被杀，整机失去响应——ping 通、SSH 与 HTTPS 全不通，
和 0039 那次一样只能走云 API 重启。重启后 swap 也没了（当初是手工 `swapon`，
没写 `/etc/fstab`），于是同样的推送又会 OOM。

所以做了这几处修正：

- `AuditTick` 默认改为 30 分钟（一天 48 次，远端最多滞后半小时）。
- 审计文件按小时分片（见上一节，这是体积问题的正解）。
- `deploy/provision.sh` 增加 swap 配置并写入 `/etc/fstab`，重启后仍生效。
- systemd 用 `MemoryHigh=700M` 软上限：刻意不用 `MemoryMax`，因为打包峰值就是这个量级，
  设更低的硬限会让每次正常推送都被杀；软限的作用是逼近时优先回收与换出，
  而不是等全局 OOM 把 sshd 一起拖下水。

半小时这个值的判断依据：一天 48 次推送，远端最多滞后半小时，"机器突然坏掉"仍然够用。

## 被否方案

- **A. 在 `record()` 里也调 `Trigger()`。** 看起来最省事，但它把"审计写入频率"
  和"冷备推送频率"绑死：审计每条记录都可能触发一次冷备 fetch，
  而这台机器每 2-3 秒就有一条审计。等于用推送风暴换实时性。
- **B. 把 `dailyTick` 从 24 小时改成 5 分钟。** 兜底的语义是"防漏"，
  不是"常规节奏"。改小会让冷备也被无谓地频繁推送，且让"兜底"这个
  独立防线失去意义——两条路径变成同一条，就只剩一个失效点了。
- **C. 审计每条记录都 commit 并立刻推送。** 正是 0039 修掉的那个故障。
- **D. 不管，接受 24 小时延迟。** 相当于承认"审计可以比冷备旧一天"。
  真出故障时，这个缺口恰好落在最需要证据的时段上。
- **E. 5 分钟周期（第一版）。** 已实测推翻：git 存全量快照，5 分钟一推
  就是 42MB/天，且打包松散对象在 1G 机器上直接 OOM。频率不是越密越好。

## 运维影响

- 远端审计的提交会比以前密（每 30 分钟一批，无变化时 fetch 后直接返回，不产生提交）。
- 审计文件按小时分片，单次提交的数据量只与当前小时的记录数有关。
- 审计的 `git log` 时间戳从此能反映"推送时刻"，不再是"最后一次有人改内容"。
- 松散对象仍需人工 `git gc`：go-git 不会自动清理。本次事故后用
  `git gc --prune=now` 把 53M/1776 个松散对象压到 768K/615KB。这个动作没有自动化，
  重建机器时需要运维手动做一次（或纳入定期任务）。
- 无变更时的空转推送不产生 commit，仓库体积不受影响（0039 的合并策略仍然生效）。
- 历史数据保持旧路径：2026-10-24 之前写入的按天文件不迁移，
  `Read` 两套格式都认。迁移只会再产生一次全量重写，得不偿失。
- 已验证：远端 `d8df526` 之后本来一条都没有，此改动后由周期推送接上，
  期间 HEAD 前进到了 `7faa2d2`。

## 复现与验证

- `TestAuditPushesWithoutTrigger`：全程不调 `Trigger`，审计必须自己上远端。
- `TestAuditTickSkippedWhilePaused`：`Pause()` 后审计周期不推，`Resume()` 后补推。
- `TestAuditTickOnlyPushesAudit`：审计周期不顺手推冷备。
- `TestAuditTickDefault`：默认 5 分钟（防止有人把上界改回一天）。
