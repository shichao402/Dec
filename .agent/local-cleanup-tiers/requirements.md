# 需求文档：本机清理分层（轻量清理 / 彻底清理）

## 引言

设置页「清理本机 Dec 资产」目前只有单一档位，一旦执行会把所有 Dec 本机落点全部清掉，包括 IDE 落地资产、MCP 条目、项目状态、secrets、SSH 与 Git 凭据配置、GCM 凭据，以及 `~/.dec` 下除 `bin`/`run` 外的全部内容（含 `config.yaml` 全局配置与 `repo.git`）。

这让两类场景无法被满足：

1. 排查问题：怀疑拉取下来的资产运行异常，希望把产物全部清掉重拉一遍，但完全不想动配置和凭据。
2. 避免重复配置：彻底清理后必须重新填私仓地址、重新配 Git 凭据、把所有项目重新导入、把所有资产重新勾选，才能恢复拉取。

本需求引入第二档「轻量清理」，把「程序可重新复现的拉取产物」与「用户手工积累、程序无法替用户重建的配置和凭据」分开处理，使一类清理动作只作用于前一类。

本需求只覆盖「本机清理」这一个动作的档位化，不改动 pull / push / prune 语义，也不实现 issue #23 的单一粗粒度聚合动作。轻量清理为 #23 的聚合动作预置「资产面重置」这一可复用能力，但两者不在同一次交付内。

## 需求

### 需求 1：清理档位模型

**用户故事：** 作为一名希望在不丢配置前提下重来资产的用户，我希望清理本机时能明确区分「只重来资产」与「全部重来」，以便按场景选择代价合适的动作。

#### 验收标准

1.1 系统 SHALL 定义且仅定义两个清理档位：`light`（轻量清理）与 `full`（彻底清理）。
1.2 WHEN 调用方未携带档位 THEN 系统 SHALL 按 `full` 执行，行为与引入档位前完全一致，不得静默降级为 `light`。
1.3 系统 SHALL 让两档共享同一套落点枚举来源，避免出现两套互相漂移的清单。
1.4 WHEN 档位为 `light` THEN 系统 SHALL 为每个候选落点标注它在本档位下属于「清理」还是「保留」。
1.5 系统 SHALL 在两个档位共用的结果结构中携带实际执行的档位标识，供后续展示与追溯。

### 需求 2：轻量清理的保留面

**用户故事：** 作为一名排查资产问题的用户，我希望轻量清理后配置和凭据都还在，以便清完直接重拉就能恢复，不需要重新配置一遍。

#### 验收标准

2.1 WHEN 执行 `light` THEN 系统 SHALL 保留 `~/.dec/config.yaml`，包括私仓地址、受管项目登记、IDE 选择与资产启用列表。
2.2 WHEN 执行 `light` THEN 系统 SHALL 保留全部凭据配置面：`~/.ssh` 下的 `dec_*` 密钥与 `config.d/dec*` 片段、`~/.ssh/config` 中的 Dec Include 行、项目 `.secrets` 下的凭据落地、项目 Git fragment、`~/.gitconfig` 中的 Dec 条目。
2.3 WHEN 执行 `light` THEN 系统 SHALL 不对 Git Credential Manager 中的 Dec 凭据执行撤销。
2.4 WHEN 执行 `light` THEN 系统 SHALL 保留受管项目登记，以及项目目录下 `.dec/config.yaml` 中的 requires 等声明。
2.5 WHEN 执行 `light` THEN 系统 SHALL 保留本地 secret 落地与隔离区内容（`~/.dec/secrets`、项目 `.secrets` 的 secret 部分、`~/.dec/pruned`），不得把「敏感性高、无法从 Git 恢复」的条目纳入本档位。
2.6 WHEN 执行 `light` THEN 系统 SHALL 清理 IDE 落地产物：各 plane 下的 `dec-*` skills / commands / rules 与内置 skill。
2.7 WHEN 执行 `light` THEN 系统 SHALL 清理各 IDE 的 MCP 配置中的 Dec 条目，仅移除 Dec 条目，不删除整份共享配置文件。
2.8 WHEN 执行 `light` THEN 系统 SHALL 清理 `~/.dec/cache` 与各项目 `.dec/cache`。
2.9 WHEN 执行 `light` THEN 系统 SHALL 清理 `~/.dec/repo.git`，并依赖既有的自动 clone 能力在下次拉取时重建。
2.10 IF 某个候选落点无法被证明属于 Dec 管理 THEN 系统 SHALL 在两个档位下都保留它，并在结果中说明保留理由。

### 需求 3：预览按档位区分

**用户故事：** 作为一名准备执行清理的用户，我希望在动手前看到「这个档位会删什么、又会留下什么」，以便判断是否需要换档。

#### 验收标准

3.1 WHEN 用户请求预览 THEN 系统 SHALL 使用与执行阶段相同的档位参数，只返回该档位下将发生的动作。
3.2 WHEN 档位为 `light` THEN 预览 SHALL 额外列出「本档位保留、但如果选择彻底清理会被删除」的条目。
3.3 预览 SHALL 保持只读，不产生任何文件副作用。
3.4 IF 预览与执行之间本机落点发生变化 THEN 执行阶段 SHALL 重新计算候选，不得复用预览阶段的路径快照。
3.5 WHEN 某档位下没有任何可清理项 THEN 预览 SHALL 返回明确结论，而不是空列表。

### 需求 4：确认门槛

**用户故事：** 作为一名担心误操作的用户，我希望两个档位的确认要求与破坏力匹配，以便不会因为确认词一样而误执行代价更大的动作。

#### 验收标准

4.1 WHEN 档位为 `full` THEN 系统 SHALL 继续要求输入确认词「清理本机」后才允许执行。
4.2 WHEN 档位为 `light` THEN 系统 SHALL 要求一次显式确认，且确认文案必须与 `full` 区分，不得让用户误以为配置与凭据会被删除。
4.3 IF 缺少有效确认 THEN 系统 SHALL 拒绝执行并返回明确指出档位的错误。
4.4 IF 档位取值非法 THEN 系统 SHALL 拒绝执行，不得回退到任一档位。

### 需求 5：结果摘要与可追溯

**用户故事：** 作为一名执行完清理的用户，我希望明确知道删了什么、留了什么、下一步该做什么，以便放心重拉。

#### 验收标准

5.1 WHEN 任一档位执行完成 THEN 系统 SHALL 返回按「删除 / 修改 / 撤销凭据 / 保留」分类的计数与明细。
5.2 WHEN 档位为 `light` THEN 结果 SHALL 点明本次保留了哪些用户手工积累项，并说明只需执行一次拉取即可恢复。
5.3 WHEN 存在失败项 THEN 系统 SHALL 逐条给出失败原因，且单项失败不影响其余条目继续执行。
5.4 系统 SHALL 在事件流与操作历史中记录本次执行的档位，使事后可判断用的是哪一种清理。

### 需求 6：恢复闭环

**用户故事：** 作为一名刚做完轻量清理的用户，我希望一次拉取就把资产恢复到可用状态，以便不需要重做任何配置工作。

#### 验收标准

6.1 WHEN 轻量清理完成 AND 用户执行一次拉取 THEN 系统 SHALL 使全部资产恢复可用。
6.2 WHEN 轻量清理完成后执行恢复 THEN 系统 SHALL 不要求用户重新填写私仓地址、重新配置 Git 凭据、重新导入项目或重新勾选资产。
6.3 WHEN 轻量清理完成 THEN 项目声明中的 requires 仍应生效，使该项目的资产集合与清理前一致。

### 需求 7：Console 交互

**用户故事：** 作为一名 Console 用户，我希望在清理面板上看到两个清晰的档位并默认落在更安全的那个，以便不需要先理解内部结构。

#### 验收标准

7.1 WHEN 用户打开设置页清理面板 THEN Console SHALL 提供档位选择，默认选中轻量清理，彻底清理需用户主动改选。
7.2 WHEN 用户切换档位 THEN Console SHALL 清空上一次的预览结果与确认输入，避免跨档位误确认。
7.3 WHEN 档位为 `full` THEN Console SHALL 保留现有的红色不可撤销警示；档位为 `light` 时 SHALL 用描述两者差异的提示，不得复用「不可撤销」措辞。
7.4 WHEN 执行完成 THEN Console SHALL 按当前档位展示结果摘要，并提示轻量清理后的恢复动作。

### 需求 8：兼容与边界

**用户故事：** 作为一名已经习惯现有清理行为的用户，我希望升级后原有调用方式不受影响，以便既有脚本与操作习惯不被打断。

#### 验收标准

8.1 WHEN 旧调用方不携带档位参数 THEN 服务端 SHALL 按 `full` 执行，返回结构保持向后兼容。
8.2 系统 SHALL 保持「Console、运行时套件、当前服务实例始终不被清理」这一既有约束，两个档位一致。
8.3 系统 SHALL 保持集成测试相关落点（`IntegrationAuthRel` / `IntegrationDecHomeRel`）的既有保护语义，两个档位一致。

### 需求 9：可验证

**用户故事：** 作为一名维护者，我希望两档的保留面与清理面都有自动化测试覆盖，以便后续改动不会悄悄放宽删除范围。

#### 验收标准

9.1 系统 SHALL 提供自动化测试，分别断言两个档位对同一组落点产出的删除/保留判定。
9.2 测试 SHALL 覆盖「轻量清理不触碰配置与凭据面」这一核心约束。
9.3 测试 SHALL 覆盖「轻量清理后执行拉取可恢复」的闭环，可使用 fake 资产面与本地 Git 仓库。
9.4 测试 SHALL 覆盖非法档位与缺少确认两条拒绝路径。

## 明确不做的事

- 不实现 issue #23 的单一粗粒度动作「让一切就绪」，本需求只交付可被其复用的档位化清理能力。
- 不新增面向 Agent 的 MCP 工具；本机清理维持仅经 Console 触发的既有面，避免扩大误操作面。
- 不改变 pull / push / prune 的语义与安全边界，隔离区行为不变。
- 不为两个档位各写一套扫描逻辑。
- 不提供「只清某个 IDE」「只清某个项目」的细粒度选择，保持粗粒度、低决策成本。

## 待讨论的取舍

- `repo.git` 是否纳入轻量清理：纳入则清理更彻底但需要重新 clone；不纳入则恢复更快，但会残留可能已损坏的本地仓库。当前需求按「纳入」编写（2.9）。
- `~/.dec/secrets` 与项目 `.secrets` 的 secret 落地是否纳入轻量清理：当前需求按「保留」编写（2.5），因为误删不可从 Git 恢复；若排查场景确实需要连 secret 一起重来，应作为独立档位或显式参数，而不是放宽轻量清理的默认范围。
