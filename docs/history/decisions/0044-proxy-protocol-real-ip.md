# ADR 0044：服务端解析 PROXY protocol，恢复真实来源地址

- 状态：已采纳
- 日期：2026-10-24
- 相关：需求 20.1（下载端点）、需求 20.4（下载记入审计）

## 背景

生产拓扑是：

```
公网 :443 ── nginx stream(ssl_preread + PROXY protocol) ──┬─ dec.firoyang.com → 127.0.0.1:8445 → dec-cloud 127.0.0.1:8444
                                                          └─ 其他域名         → 127.0.0.1:4443
```

nginx 在 443 那一跳就写入了真实来源地址，但中间的 `8445` 是一个只做字节转发的
stream server，成立它的原因很具体：dec-cloud 早期不认识 PROXY 头，TLS 握手会读到
一个莫名其妙的文本前缀而失败，于是加一跳把它剥掉。

代价是 dec-cloud 看到的 `RemoteAddr` 永远是 `127.0.0.1`。

这个问题最初是在审计里发现的（`remote_ip` 字段对公网请求没有取证价值），
但顺着查下去发现更要紧的是另一件事：**下载限流也是按 IP 分桶的**。

`rateLimiter` 用 `clientIP(r)` 作为桶键，限额是每分钟 30 次。当所有公网请求
都呈现为 `127.0.0.1` 时，它们共用同一个桶——任意一个爬虫把 30 次额度刷完，
接下来一分钟内所有人的下载都返回 429。这不是理论风险：`/download/` 是无证书、
公网匿名可访问的端点，正是最容易被脚本扫的地方。

所以这不再是一个"审计字段不准"的问题，而是一个可用性问题。

## 决策

让 dec-cloud 在 listener 层解析 PROXY protocol；nginx 在 443 那一跳写入头之后，
**8445 只做纯字节透传**，不消费、也不重新生成这个头。

具体做法：

- `internal/cloudsvc/proxyproto.go` 实现 v1（文本）与 v2（二进制）两种格式，
  包装成一个 `net.Listener`，在首次访问连接时解头，把来源地址填进 `RemoteAddr`。
- `Config.ProxyProtocol` 控制开关，命令行 `-proxy-protocol`，**默认开启**。
- 只在监听回环地址时允许开启，启动时校验（`requireLoopbackListen`）。
- nginx 的 8445 段写成 `listen 127.0.0.1:8445;` + `proxy_pass 127.0.0.1:8444;`，
  不带任何 `proxy_protocol` 指令。

## 为什么不是别的方案

**去掉 8445 那一跳，让 443 直接转发到 8444。** 这看起来最干净，但要同时改
SNI 分流的 map、8445 的 server 块、systemd 单元里的端口引用，以及回滚脚本里
的备份内容。改动面越大，出问题时越难判断是哪一处。而 listener 层解析是纯应用内
改动，拓扑与回滚路径都不动。

**信任 `X-Forwarded-For`。** 绝对不行。PROXY protocol 头由 nginx 在 TCP 层写入，
客户端无法越过它伪造；而 XFF 只是一行 HTTP 头，公网请求可以写任何值。
信任它等于让请求者自报来源，限流会被直接绕过——那比"地址不准"更糟。

**在 8445 用 `proxy_protocol` 但保持剥掉。** 那是现状，问题依旧。

**在 8445 写 `proxy_protocol on` 让 nginx「重新附加」头。** 这是最初的设计，
实测证明理解错了 nginx 的语义，见下面第 3 条。

## 三个实现细节，都是踩过的坑

### 1. `RemoteAddr` 也必须触发解析，不能只挂在 `Read` 上

最初把解析放在 `Read` 里（第一次读时解头），因为 TLS 握手一定会读，看起来必然
先于任何 `RemoteAddr` 调用。但 `http.Server` 在填 `http.Request.RemoteAddr` 时
会**单独**问 `RemoteAddr()`，而那一刻是否已经读过数据并无保证。

如果解析只挂在 `Read` 上，就可能出现"头还没解、地址已取走"，结果是限流与审计
拿到的仍是 `127.0.0.1`——修复看起来生效了，实际没有。
`TestProxyHeaderReachesHandler` 先取 `RemoteAddr` 再读数据，就是冲着这个场景写的。

### 2. 不带头时必须完全正常

这是灰度发布的前提。服务端先上线、nginx 后改，两步之间所有连接都不带 PROXY 头。
如果这时解析器报错或吞掉字节，整个服务会在部署那一刻不可用。

所以"没有头"不是错误：`Peek` 前 12 字节既不匹配 v2 签名、也不是 `PROXY `，
就当普通 TLS 字节流继续。`TestNoHeaderPassesThrough` 守住这条。

### 3. nginx 的 `proxy_protocol` 是「消费 / 重新生成」，不是「透传」

这是最贵的一个坑，因为它看起来完全合理：443 已经附了头，8445 只要再附一次就能送到
8444。按这个理解写出来的配置是：

```nginx
server {
    listen 127.0.0.1:8445 proxy_protocol;   # 错
    proxy_protocol on;                      # 错
    proxy_pass 127.0.0.1:8444;
}
```

实测（tcpdump，2026-10-26）结果与预期相反：

```
8445 入口：（从 443 传来）PROXY TCP4 43.161.239.208 10.5.0.9 40812 443
8444 入口：（8445 发给上游）PROXY TCP4 127.0.0.1 127.0.0.1 47670 8445
```

两条语义各自独立，且都不是透传：

- `listen ... proxy_protocol` 让 nginx 在**这一跳消费**掉进来的头，头被吃掉后就没了。
- `proxy_protocol on` 让 nginx 向上游**重新生成**一个头，来源填的是它此刻的对端，
  也就是本机地址。

于是真实来源在两处同时丢失，服务端解析出来的永远是 `127.0.0.1`。正确写法是两条都不写，
让 443 写入的字节原封不动流到 8444：

```nginx
server {
    listen 127.0.0.1:8445;
    proxy_pass 127.0.0.1:8444;
}
```

改完的验证方法：抓 8444 入口的包，头里的源地址应当是真实公网 IP、两个端口是
`<客户端端口> 443`（而不是 `<端口> 8445`）；再看审计里新产生的 `download` 记录，
`remote_ip` 应等于客户端出口 IP。两条都对才算真的生效——只看"服务能起来"会漏掉这个坑，
因为错误的配置下服务一样正常，只是地址悄悄变成了本机。

## 部署顺序（不可反）

1. 先部署带解析的服务端。它对不带头连接完全兼容，nginx 未改时无影响。
2. 再改 nginx 的 8445 为纯字节透传（不带 `proxy_protocol`），reload。

反过来的话，旧服务端会收到不认识的文本前缀，TLS 握手失败，所有设备同时断连。
这个顺序已写进 `deploy/README.md`。

## 影响

- 下载限流按真实来源分桶，一个来源刷量不再影响其他人。端到端验证见
  `TestRateLimitSeparatesProxiedSources`：A 用满额度返回 429 后，B 的首次请求仍成功。
- 审计里的 `remote_ip` 对公网请求恢复取证价值。
- 未经 nginx 的本机直连（健康检查、调试）仍呈现为回环地址，共用一个桶。
  这是有意的取舍：它们的量极小（健康检查按分钟计），而为了区分它们去信任
  HTTP 头会打开伪造来源的口子。
- nginx 的 `LOCAL` 命令（健康检查等）不采信来源字段，按底层地址处理。

## 未采纳：把限流改成按其他维度

有人会问为什么不干脆按设备 ID 或文件路径限流。这是因为 `/download/` 是无证书
公网端点，请求里没有设备身份可用；按文件限流则会让"同一文件被多人下载"互相影响，
仍然是一个爬虫影响所有人。来源 IP 是唯一在这个端点上既可得、又不可伪造的维度。
