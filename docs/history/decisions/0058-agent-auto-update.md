# 代理静默自动更新：签名清单 + 两段式替换

## 背景

需求 19.3 规定「代理 SHALL NOT 自动更新」，更新靠用户自己下载替换。实际使用中，
每次客户端发版后每台设备都会进入「版本不对齐、停止同步」状态，直到人去逐台重装。
设备越多越不可行，而且不对齐期间资产不下发，等于发版即断供。

不自动更新的原始顾虑有两个：一是替换正在运行的二进制本身有文件占用与锁的问题；
二是「服务端给什么就装什么」把服务端变成了所有设备的执行入口，服务端被攻破就是
全部设备被攻破。

## 决策

1. 推翻需求 19.3：代理静默自动更新，不弹确认。可用 `DEC_AUTO_UPDATE=0` 关闭。
2. 信任链：CI 用 ed25519 私钥签名 `release.json` 的原始字节，生成 `release.json.sig`。
   私钥只在 GitHub 仓库 Secret `RELEASE_SIGNING_KEY`，服务器上没有；公钥编译进代理
   （`release.TrustedKeys`，列表形式便于轮换）。代理先验签，再用清单里的 sha256 和长度
   逐个校验下载的二进制。CI 签完立即用内置公钥回验，不匹配就让发布失败。
3. 防降级：只在本机版本低于清单的 `required_client` 时更新；清单版本必须高于本机版本，
   且不低于它自己的 `required_client`。被回放的旧清单（同样签过名）不会让代理变旧。
   只改服务端的发布沿用旧的要求版本，不触发更新。
4. 两段式，两个进程：
   - 代理进程：定时（首次 1 分钟后，之后每小时）或握手发现不对齐时检查，下载到
     `update/staged/<版本>` 并校验，把自身复制成 `update/dec-updater`，写 `update/plan.json`，
     以脱离服务的方式拉起 `dec-updater update-apply --plan ...`。这一段不碰运行中的文件，
     任何失败代理照常运行。
   - 更新进程：拿 `update/apply.lock`（15 分钟过期）→ 停服务 → `target` 改名为 `target.old`
     → 放入新文件 → 起服务 → 健康检查（先跑新文件的 `version`，再等本机页面 `/api/status`
     报出新版本，最多 90 秒）。任一步失败就换回 `.old` 并重启。结果写 `update/last.json`，
     代理下次启动时记日志，失败时发一次系统通知。同一版本失败后冷却 6 小时。
   - 更新进程用的是旧版本二进制的拷贝：它已经在这台机器上证明能跑。先改名再放新文件，
     是因为 Windows 允许给运行中的 exe 改名但不允许覆盖。
5. 脱离服务：Linux 用 `systemd-run --user --collect`（失败退回 setsid）；macOS 用 setsid；
   Windows 注册一次性计划任务 `DecAgentUpdate`（无触发器、限时 15 分钟）后立即运行。
   否则停服务时会把更新进程一起杀掉。
6. 适用范围：只有「以已注册服务身份运行的默认实例」才自动更新（正式版本号、默认状态目录、
   服务定义指向当前可执行文件）。前台调试、隔离状态目录、本地 dev 构建一律不更新。
   托盘只在本机已安装且清单里有对应产物时一起替换。
7. 下载通道放行 `release.json` 与 `release.json.sig`，原样输出部署时放入的字节（服务端重新
   序列化会让验签失败），不记审计（每台设备每小时一次的轮询会淹没真实下载记录）。
8. 手动入口：`dec-agent update` 立即检查一次，资格与自动更新相同。

## 后果

- 发版后设备在约一小时内自行对齐，不再需要逐台重装。需求 19.5 的「需要更新」提示只在
  不具备自动更新资格的实例上出现。
- 服务器被攻破也无法让代理安装任意二进制；能做的最多是停止提供清单，让设备停在当前版本。
- 私钥丢失时无法发出设备肯装的版本，只能逐台手动安装带新公钥的版本。私钥备份在
  维护者本机 `~/.config/dec/release-signing.key`。
- 轮换公钥要分两步：先发同时信任新旧公钥的版本，设备都升上去后再换私钥、去掉旧公钥。
- 第一个带自动更新能力的版本本身仍需手动安装一次。
