# ADR 0061：SSOT 本机历史保留 180 天，更早的由冷备存档

- 状态：已接受（待发版）
- 日期：2026-10-31
- 相关：需求 1.3、1.6、11.6、14.1、15.1、15.2，ADR 0043

## 背景

用户提出：资产历史应有 180 天回收，并提供查询历史与恢复接口，否则云端
SSOT 风险较高。

查证后的现状：

- 查询与恢复早已具备：协议方法 `history` / `rollback`，管理面「历史」页
  逐条「回滚到此」，MCP 的 `dec_history`。回滚刻意只开放给管理面与 host CLI
  （`identity.CanManageDevices`），本次不改。
- SSOT 从未做过 git gc。线上 9 天、150 个提交：`.git` 3.7M，其中松散对象
  818 个占 3.4M，打包后只有 600K。体积问题来自"没人打包"，不是历史长。
- 直接截断历史（重建提交链）有两个硬冲突：违反需求 1.6「SHALL NOT 改写历史」；
  冷备推送前的祖先校验（需求 15.2）会永久失败，恢复只能 force-push，而那被禁止。

## 决策

本机 SSOT 只保留最近 180 天历史，更早的由冷备仓库 `dec-cloud-backup` 完整保存。
实现是把本机仓库变成 shallow，而不是改写提交：

1. 每日兜底周期在冷备推送之后调 `Store.Gc()`。
2. 边界取"保留期开始前的最后一个提交"。它的内容就是保留期起点的完整快照，
   留下它，保留期内第一个提交才有父提交可比，也能回滚到"保留期开始时"。
3. 安全条件：边界必须是冷备远端跟踪引用（`origin/<branch>`，推送前刚 fetch 过）
   的祖先或其本身。冷备未配置、从未推成功、或落后于边界时只打包不截断，
   并在结果里说明原因。
4. 写 `.git/shallow` → `reflog expire` → `git gc --prune=now`，然后重新
   `PlainOpen` 换句柄。
5. 未到截断时，松散对象达 256 个才打包，避免空闲日白跑。

为什么这不算改写历史：没有任何提交被重写，哈希全部不变，HEAD 不变；冷备远端
仍是只追加的完整链。本机只是不再持有旧对象。

## 取舍

- 全程持写锁 `mu` 与新增的仓库句柄锁 `repoMu`。审计仓库不能这样做（大、写频繁，
  ADR 0043），SSOT 很小，线上副本实测回收亚秒级。持锁换来两点：可以安全用
  `--prune=now`；读路径永远不会碰到被删的 pack。锁序固定为先 `mu` 后 `repoMu`。
- `History` 不再用 `repo.Log`：后者遇到 shallow 边界缺失的父提交会报
  object not found。SSOT 只由本进程提交、永远线性，沿第一父提交走到边界即可。
- 超出保留期的回滚报 `not found`，错误信息写明"更早的版本在冷备仓库里"；
  历史响应新增 `retention_days`、`retained_since`、`truncated` 与条目级
  `baseline`，管理面与 MCP 描述同步说明。
- 不新增"从冷备恢复"接口。180 天之前的版本属于取证与灾备场景，冷备是
  普通 git 仓库，可直接检出；为它在线上服务里加一条读远端的路径，
  收益不抵复杂度与权限面。

## 验证

- `ssot` 包：无冷备不截断、冷备未覆盖边界不截断、截断到正确边界且 HEAD 不变、
  起点快照可读、回收后可写且非 force 续推、冷备仍是完整链、重复回收幂等、
  全部在保留期内时什么都不做。
- `backup` 包 `TestPushContinuesAfterSsotRetention`：用真实的 go-git Pusher
  （fetch + 祖先校验 + push）验证回收后冷备照常推送。
- 生产 SSOT 副本演练：今日回收只打包（3.7M → 516K，不截断）；模拟一年后
  截断为 1 个提交、HEAD 不变，随后写入并续推成功，冷备 151 个提交完整。

## 影响

- 灾备重建（需求 11.6）从冷备克隆，拿到的是完整历史，不受影响。
- 部署机需要系统 git（审计回收早已依赖）。
- 截断需要冷备至少成功推送过两次（首推后再 fetch 一次才有跟踪引用）；
  线上已满足。
