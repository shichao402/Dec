# ADR 0045：代码仓库保持公开，改为守住「仓库里不能有真东西」

- 状态：已采纳
- 日期：2026-10-26
- 相关：已定决策 10、13、19，需求 15.2、21.1、21.7、22

## 背景

需求文档原先把「代码仓库私有化」写死成一个前置条件：需求 22 要求 `shichao402/Dec` 必须是私有仓库，已定决策 13 把「不再是公开项目」当成这次重构定性的一部分，任务清单第一步就叫「仓库私有化」，并且要求在写第一行代码之前完成。

2026-10-26 核查 GitHub 现状，`shichao402/Dec` 实际是 `visibility=PUBLIC`、`isPrivate=false`，既没有改私有，分支保护也没开（`GET /branches/main/protection` 返回 404）。也就是说文档、任务清单与实际状态三者不一致：文档写私有，实际是公开。

这个不一致必须先解决方向问题，而不是补一个 `gh repo edit --visibility private` 了事。

## 决策

### 一、方向反转：代码仓库保持公开

选公开而不是补私有，理由不在「省事」，在于私有化从来就没提供过它看起来提供的东西：

- 已定决策 10 已经明确说过，代码不公开只是附加收益，SHALL NOT 被当作安全边界。既然如此，为一个不构成防线的属性去改写历史、切换可见性、再承受「私有仓库用不了分支保护和 environment」的免费套餐限制，收益是负的。
- 私有仓库在免费套餐下拿不到分支保护，也拿不到 environment 保护规则。公开仓库反而两者都有。也就是说，私有化在免费套餐下让仓库的保护能力变弱了，这与「提高安全性」的初衷相反。
- 代理本来就是不分发签名、不内嵌服务地址的通用二进制（需求 2.9），服务端也要求所有客户端对齐版本。代码被看到并不会让攻击者多出可用的入口——真正的攻击面是 443、22 和 GitHub 账户，这三样都跟代码可见性无关。

所以「公开」不是妥协，是把一个本来就只是心理安慰的约束换成了真实可用的保护能力。

### 二、结论反过来：正因为公开，仓库里不能有真东西

方向一反转，原来那条「私有化只是附加防线，即使泄露也不该暴露信息」的松弛表述就不成立了。现在提交历史对所有人可检索，任何一次 `git log -p` 都能翻出来，所以要求从「最好不要硬编码」升级成「SHALL NOT 出现」：

- 真实凭据：根密钥、deploy key、Actions secret、Bitwarden 凭据、企业微信 webhook 地址。
- 真实公网 IP、SSH 端口转发细节、服务器上的绝对路径和账户名。
- 这些一律走 GitHub Actions secret、服务器本地文件（`/etc/dec-cloud/`）和仓库外配置。

同时明确划出可以保留的东西，避免把排查做成无用功：

- `dec.firoyang.com` 保留。域名是公开信息，证书透明日志（CT）里本来就能查到，删掉它既无意义也会让文档失去可读性。
- `127.0.0.1`、`0.0.0.0` 等回环地址保留。它们不指向任何真实主机。
- 真实公网 IP 不保留。这是唯一必须挡住的网络层信息。

### 三、分支保护开启，但只开最小范围

免费套餐的限制值得澄清，因为这里最容易误判：分支保护在 GitHub Free 下确实可用，但只在公开仓库可用（私有仓库要 Pro 及以上）。查 `shichao402/Dec` 当天是 `visibility=PUBLIC`，所以这项能力是拿得到的——`GET /branches/main/protection` 返回 404 的意思是「这个分支还没设保护」，不是「套餐不支持」。

开启时的范围按最小必要来定，只禁两件事：

- 禁止强制推送（`allow_force_pushes=false`）。
- 禁止删除 `main`（`allow_deletions=false`）。

刻意不开启的几项，理由都是它们会挡住单人开发而不是挡住风险：

- 不要求 PR 评审。单人项目没有第二个人能批准，开了等于把自己锁在外面。
- 不要求状态检查。CI 已经有独立的质量门，把它绑成合并前置条件只会让「CI 挂了要紧急修」变成「连修 CI 的提交都推不上去」。
- 不要求线性历史、不要求签名提交。两者都与当前提交习惯冲突，收益不足以补偿摩擦。

另外必须显式打开 `enforce_admins=true`。GitHub 的默认行为是把仓库管理员排除在保护规则之外，管理员仍可强推和删分支——不打开这一项，等于设置了一个只对自己无效的保护。已实测确认：开启后 `git push --dry-run origin main` 正常通过，日常直接推送不受影响。

**保护的边界也要讲清楚。** 禁强推防的是「历史将来被覆盖」，防不了「内容已经流出去」。因此需求 22.3 的结论不变：一旦有凭据进入过历史，一律轮换，不靠回滚历史来补救。这两件事互补，不是互相替代。

### 四、连带调整的其他几处

- 需求 21.7：部署 secret 从「仓库级 secret + 等效措施」改为「environment secret + environment 保护规则只允许 `refs/tags/v*`」。tag 与 commit 的一致性校验保留，因为它防的是另一件事（伪造部署包），不因为有了 environment 就多余。这是部署链路上的那一层保护，与分支保护负责的「分支历史不可被覆盖」是两件不同的事。
- 需求 21.1：删掉「私有仓库 Actions 额度有限」的表述。公开仓库不受该额度限制，但 macOS runner 仍按 10 倍计费且排队更久，所以「只用 Linux runner，托盘除外」这条约束不变，理由改写为排队与成本而非额度。
- 需求 2.8：公开仓库的 Release 不再需要登录才能下载，措辞从「私有仓库的 Release 只作备用」改为「公开仓库的 Release 只作备用下载路径，以服务端下载通道为准」。

需求 15.2 不动结论，只限定范围：它讲的是冷备和审计这两个仍然私有的仓库。这两个仓库装的是加密后的真实资产和审计记录，属于运行数据，与代码仓库分开是对的。

## 影响

- 仓库无需切换可见性，不会触发「公开转私有会忽略已配置的 environment 保护规则和环境机密」这个 GitHub 行为。
- `main` 已开启分支保护（只禁强推与删除，`enforce_admins=true`），历史不会被覆盖、分支不会被误删。实测 `git push --dry-run origin main` 正常，日常直接推送不受影响。
- 部署 environment 保护规则可以正常启用，部署 secret 因此被限定在 `refs/tags/v*` 上，需求 21.7 比原方案（仓库级 secret，无范围限制）更严。
- 这两项保护都在 GitHub Free 下对公开仓库免费，不需要升级套餐。
- 新增一条长期约束：任何提交进仓库的内容都视为已公开。评审新代码、新增配置文件、写文档时都要按这个前提检查。
- 提交历史中的旧内容不会因为这次决策而变干净。历史排查与凭据轮换仍然是必须做的事，只是它现在从「私有化之前的前置动作」变成了「持续有效的纪律」。

## 未采纳的方案

**补一次 `gh repo edit --visibility private`，把文档改回去**：改动最小，但会同时失去分支保护和 environment 保护规则（免费套餐），最终的安全状态比公开更差；而且它把一个不构成防线的属性继续当成防线来维护，后续会反复出现「文档说私有、实际是公开」这类不一致。

**改私有并升级到 GitHub Pro**：能同时拿到私有 + 分支保护，但为一个已确认不构成安全边界的属性付费，且信任模型（已定决策 10）没有任何实质变化。

**公开但仍然按「反正没人在看」对待提交内容**：这是最危险的选项。公开仓库的提交历史会被爬虫与搜索引擎收录，凭据一旦进入历史，轮换之前的窗口期就是真实泄露窗口。
