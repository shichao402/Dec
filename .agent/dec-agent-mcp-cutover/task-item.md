# 实施计划

前置：工作区里还有没提交的 `delete_asset` 按路径删除修复，以及文档合并的改动。开始前要先把它们分成两个独立提交。MCP 的“删除资产条目”工具依赖这次修复。

- [ ] 1. 源码断代：盘点并删除旧代码
- [ ] 1.1 生成新一代依赖图并确定删除清单
  - 用 `go list -deps ./cmd/dec-cloud ./cmd/dec-agent` 得出保留包集合，其余 `internal/`、`cmd/`、`tools/` 一律进入删除清单
  - 核对计划中约定保留的 `internal/secrets`、渲染、vars 模块：仍被引用的保留，否则删除
  - 在当前 HEAD 打 `legacy-final` 标签
  - _需求：3.1、3.2、3.3_

- [ ] 1.2 执行删除并收敛构建
  - 删除 `cmd/dec-server`、`cmd/dec-exec`、`cmd/dec-host-setup`、`cmd/dec-registry`，以及清单里的旧包、旧工具和它们的测试
  - 把 `Makefile` 的 build、test、install 目标改为只面向 `dec-cloud` 和 `dec-agent`
  - 执行 `go mod tidy`，移除只被旧代码使用的依赖；确认 `go build`、`go vet`、`go test ./...` 全部通过
  - 确认 `release.yml` 的产物名、部署脚本、协议版本都没变
  - _需求：3.2、3.4、3.6、3.7_

- [ ] 1.3 编写依赖守卫测试
  - 新增测试：解析 `dec-cloud` 和 `dec-agent` 的依赖图，只要出现已删除包的路径前缀就失败
  - 同一个测试扫描源码，出现“后续阶段再接上”这类无主推迟注释也失败
  - _需求：3.5、4.5_

- [ ] 2. dec-agent 的 MCP 协议层
- [ ] 2.1 用官方 SDK 替换 `/mcp` 转发壳
  - 在 `internal/agent` 新建 MCP 服务，基于 `modelcontextprotocol/go-sdk` 的 Streamable HTTP handler 挂到 `/mcp`，删除旧的 `handleMCP`
  - 握手在本地完成，不再转发给云端的 `initialize`
  - 确认 Host、Origin 守卫仍然包在 `/mcp` 外层，不带 Origin 的本机客户端可以连接
  - 用 SDK 客户端写单测：握手、`notifications/initialized`、空的 `tools/list`
  - _需求：1.1、1.2、1.3、1.9_

- [ ] 2.2 定义工具清单并统一转发到云端
  - 按新协议实现最小工具集：状态、列出资产、读取资产、写入资产、按路径删除资产条目、列出密钥元数据、写入密钥、删除密钥、历史、项目登记与订阅的读取和修改
  - 每个工具都要有输入 schema 和中文描述，写明“整体替换、少传即删除”“写入立即推送并进入审计”等副作用
  - 所有调用经 `callRemote` 转发，来源固定为 `mcp`；清单外的工具名返回 MCP 错误，不转发
  - 不提供读明文、设备管理、回滚、轮换根密钥这几类工具
  - _需求：1.4、1.5、1.6、1.7_

- [ ] 2.3 错误语义与测试
  - 未登记、版本不对齐、维护中、云端拒绝这几种情况，都映射成能说清原因的 MCP 工具错误，不返回空结果
  - 用伪造的云端写测试：每个工具转发的方法名和来源都正确；被禁的工具不可见、也调不通；各类错误的文案能定位原因
  - _需求：1.5、1.6、1.8_

- [ ] 3. 本机 IDE 自动接入
- [ ] 3.1 实现 `dec` 内置条目的写入与移除
  - 识别 Claude、Codex、Cursor 的用户级 MCP 配置路径；配置目录不存在的宿主直接跳过，不替它创建
  - JSON 和 TOML 都只改 `dec` 这一条，原子写入，保留其他条目和格式
  - 代理启动时写入；监听端口变化时更新；`uninstall` 时从各宿主移除
  - 写单测：已有其他条目的配置改完后只有 `dec` 变化，删除时也只删 `dec`
  - _需求：2.1、2.2、2.3、2.4、2.5_

- [ ] 3.2 新增 `dec-agent mcp-config` 命令
  - 打印当前条目内容，以及每个宿主的状态：已写入、已跳过（附原因）、写入失败
  - 更新 `docs/USAGE.md` 的 MCP 一节：说明自动接入、排查命令、工具清单与限权
  - _需求：2.6_

- [ ] 4. 真实链路验收
- [ ] 4.1 编写 MCP 验收客户端与 `scripts/acceptance.sh`
  - 基于官方 SDK 写一个小客户端（放在 `cmd/` 以外的验收目录），由脚本调用
  - 依次检查：`/admin` 返回 200；`/api/status` 显示 `aligned: true`；各宿主都有 `dec` 条目；握手；`tools/list` 包含全部预期工具，且不含被禁工具；状态；列出资产；读取 relkit
  - 写入临时 bundle `dec-acceptance-<时间戳>`，订阅到一个临时测试项目，确认文件已落到本地，再删除 bundle，确认落点已清理
  - 用 trap 保证中途失败也会清理，并打印残留项
  - _需求：4.1、4.2、4.3_

- [ ] 4.2 发布新版本并对生产执行验收
  - 打 tag，经 CI 发布新的 `dec-agent` 与 `dec-cloud`；本机升级代理，重启 launchd 服务
  - 对生产云端运行 `scripts/acceptance.sh`，全部通过才算完成
  - 在需求文档末尾补一张对照表，每条验收标准对应一项脚本检查或具名测试，任何一条没有对应都不算完成
  - _需求：4.1、4.2、4.4、3.7_
