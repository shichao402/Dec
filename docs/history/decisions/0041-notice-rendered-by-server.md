# 0041 说明行由服务端渲染时写入，代理只落字节

## 背景

2026-10-23 生产故障的直接原因不是审计、也不是磁盘，而是一行说明文字。

需求 6.4 要求托管文件开头带一句「由 Dec 管理，本地修改会被覆盖」。
原实现是代理在落盘时插到内容前面。这让两侧对同一份内容的哈希算不出来：

- 代理按**自己写下的字节**算哈希（含说明行），上报给服务端当核对清单；
- 服务端按**SSOT 里的字节**算哈希（不含说明行），拿它跟清单比。

两个值对任何文件都不相等，于是每一轮对账都判定为"有差异"，把同一批文件
再下发一次，代理再写一次、再算一次，下一轮还是不相等。单台设备因此陷入
无限重写循环，日志里每次循环留一条 sync 记录，最终累积到 8.4 万条，
把 `.git` 撑到 5.7G、写满 40G 系统盘，内核 I/O 阻塞到 sshd 无法 fork，
整机失联 65 分钟（磁盘与提交策略的部分见 [0039](0039-audit-commit-coalescing.md)）。

值得单独记下来的是：**当时所有测试都是绿的**。测试自己伪造"代理会算出什么"，
前提就写错了——它假设代理写下的字节等于收到的字节，而这恰恰是不成立的那一条。
对账算法本身没有 bug，bug 在两个组件对"同一份内容"的定义不一致。

## 决策

1. **说明行只在服务端渲染阶段写入。** 位置在 `render.go` 组装 `proto.File` 之后、
   计算哈希之前：`pf.Content = notice.Apply(...)`，随后
   `Hash: ssot.SumHex([]byte(pf.Content))`。下发的 `Content` 从此就是最终落盘字节，
   哈希自然包含说明行，两侧对的是同一串字节。
2. **代理一行都不改写。** `apply.go` 的 `FormatWhole` 分支直接写 `f.Content`，
   并按同一份 `f.Content` 算哈希返回。`withNotice` 退化为幂等空操作，
   只留注释说明"说明行不在这里加"。
3. **规则收敛到一个包。** 新建 `internal/notice`，`Applies` 判断该不该加、
   `Apply` 负责加。服务端与代理共用它，不存在两份实现漂移的可能。
4. **跨层测试用真实代码，不伪造哈希。** `agent_e2e_test.go` 用真实的
   `agent.Writer` 落盘、真实的 `agent.HashFile` 从磁盘读回、喂给真实的
   `render.Sync`，断言第二轮 `Batch == nil`。这条测试对说明行的位置、
   代理是否偷改内容、两侧哈希算法是否一致全部敏感。

## 为什么不是另外两个方向

- **代理算哈希前先剥掉说明行。** 能修，但把"哪一行算说明"变成两侧都要知道的隐式约定。
  内容里恰好出现同样的句子（用户抄过去的）就会剥错，且以后改说明文案要同时改两处。
  它修的是症状，病根是"同一条规则有两个执行者"。
- **服务端下发时把说明行一起算进哈希，代理照旧加。** 那服务端必须预测代理会加什么，
  等于把代理的实现细节复制到服务端，是同一类耦合的另一种写法。

方向一之所以是正解：它让"下发的字节"与"落盘的字节"成为同一个东西，
对账协议从此不需要知道说明行的存在。

## 顺带修掉的两个既有缺陷

原来的 `notice` 逻辑在代理里，只按扩展名 `.md/.mdc` 判断，写法一律 HTML 注释：

- **`.yaml/.yml` 落点用 `<!-- -->` 是非法语法。** 整份 YAML 解析失败，
  用户看到的是"配置突然不生效"，而 Go 测试完全正常。现在改用 `# `。
- **`.mdc` 带 front matter 时说明行插在前面会破坏规则。** front matter 必须留在第一行，
  否则 Cursor 认不出 `description`/`globs`，规则静默失效。现在插到 front matter 之后。

这两类问题的共同点是：不会让任何测试变红，只会让用户的 IDE 悄悄不加载配置。
因此 `TestNoticeKeepsFilesParseable` 专门断言 YAML 里不出现 `<!--`、
`.mdc` 首行必须是 `---`。

## 被否方案

- **A. 干脆不加说明行。** 需求 6.4 明确要求，且它确实是用户唯一的现场提示
  （文件在 IDE 里被覆盖后，只有这行能解释为什么改不回去）。
- **B. 说明行写进文件末尾。** 对 `.md` 尚可，对 YAML/JSON 类文件末尾插入同样可能破坏结构；
  且"在开头就知道这文件不归我管"比翻到末尾更符合提示的目的。
- **C. 只在首次下发时加，后续更新剥离再重加。** 需要维护"上次加了什么"的状态，
  而代理按设计不保存下发清单（需求 5.2），做不到。

## 验证

- `TestSyncConvergesWithRealAgent`：一轮下发 + 真实落盘后第二轮必须无差异。
  用注入故障法验证过它有效——把代理改回"落盘时加说明"，此测试立即失败并列出
  3 个要重发的文件。
- `TestNoticeKeepsFilesParseable`：YAML 落点不含 `<!--` 且以 `# ` 开头，`.mdc` 首行是 `---`。
- `TestApplyWholeFileWritesExactBytes`：代理写下的字节与收到的字节逐字节一致。
- `TestApplyDoesNotInjectNotice`：代理不注入说明。
- `render_test.go` 三处断言从"内容等于原样"改为"说明行 + 原内容"的精确匹配，
  没有放松成 `Contains`——放松就再也测不出重复添加了。

## 运维影响

- 升级后第一轮对账会给**所有**托管文件下发一次新内容（多了说明行或换了注释写法），
  这是预期的一次性变化。
- 旧代理天然兼容，不需要同时升级。它原来的 `withNotice` 里有
  `strings.Contains(content, managedNotice)` 的幂等检查，而新服务端下发的内容
  已经包含这句文本，于是旧代理会原样写入、按同一份字节算哈希，两侧自然一致。
  这一点很关键：它意味着只升级服务端就能停止重写循环，不必冒险先推客户端。
  真正必须升级代理的场景只有一种——服务端仍在下发不含说明的内容（即回滚服务端），
  那才会退回旧行为。因此发布顺序应是先服务端、后客户端，`required_client` 不急抬。
- 落点内容从此与服务端 SSOT 严格一致，`dec` 侧的任何改写都会在下一轮被发现并覆盖，
  这正是需求 6.1「不做双向同步」想要的效果。
