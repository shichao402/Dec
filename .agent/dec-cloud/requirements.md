# 需求文档：Dec 云端化（Dec Cloud）

## 引言

现在的 Dec 是重客户端架构。Console、运行时套件、资产和密钥都要在各台机器上手动更新，个人资产还是双向同步，更新负担和漂移问题一直没解决。

本方案把 Dec 整体迁到一台个人云端服务上，各机器只留一个超薄的通讯代理：

- 云端服务是唯一的 SSOT，资产和密钥都在里面，同时负责流程。资产和加密后的密钥放在服务内部的 git 里，使用者看不到 git。
- 代理只负责鉴权、安全通讯，以及往 Dec 落点写文件。代理是不签名、不内嵌服务地址的通用二进制，安装后由用户配置服务端。版本由服务端统一规定，不对齐的设备会被拦住，并提示从服务端下载要求版本。
- 发布和部署由 GitHub CI 在打 release tag 时一次完成：服务端和客户端从同一个 tag 构建，部署服务端的同时把客户端二进制放到服务端的下载通道。
- 密钥用根密钥加密后存进 git。根密钥以受保护文件的形式存放在服务器本地，不进入 git 和冷备，服务启动时自动加载。
- Bitwarden 不再是运行时依赖，只作为根密钥的冷备：初始化时存入一份，服务器重建时取回。
- 所有通道都是单向的。读取链路从云端到设备，本地副本只读。写入链路是独立的同步请求，直接进云端，不经过本地文件。
- 资产和密钥都在 Dec 自己的界面里管理。
- 代码仓库保持公开，冷备仓库和审计仓库保持私有（里面是加密后的真实资产和审计记录，属于运行数据）；正因代码人人可见，密钥和真实服务器信息一律不进仓库。

本产品只有一个用户，就是作者本人。因此不设账户和角色体系：已登记的设备就是“我”，设备全丢时用 Bitwarden 主密码和 2FA 证明身份（见需求 18）。

### 已定决策（讨论结论，不再重开）

1. 密钥不再存放在 Bitwarden。密钥按值加密后和资产存在同一个 git SSOT 里，共用历史、回滚和冷备。
2. Bitwarden 只作为根密钥冷备，直接复用现有 `internal/secrets` 的 API 实现（`IdentityClient` 的 Prelogin/Login 与 2FA、`vaultkey` 解密、`APIClient` 的条目读写），不引入 `bw` CLI。主密码和 2FA 在初始化或恢复界面上手动提供，用完立即登出并清除，服务不持久保存任何 Bitwarden 凭据。
3. 现有 Bitwarden 账户是 Dec 专用的，密钥内部不再划分敏感等级。
4. 公司合规不构成约束，资产和密钥都是个人数据。
5. 资产 git 由服务通过 go-git/libgit2 直接提交，不对外开放任何 git 协议。
6. 不做任何双向同步策略。本地落点是只读缓存，本地改动不回收，也不转成提交，一律以云端为准覆盖。
7. 资产和密钥的写入都走同步请求，在一次请求内完成校验和提交。不设异步队列，不设提交状态机，也不设草稿层。
8. 加密使用成熟方案（如 age 或 libsodium），不自行实现密码学原语。
9. 根密钥存放在服务器本地文件，服务启动时自动加载，不设封存/解封流程。加密只用来保护离开服务器的数据（git 冷备），不负责防御服务器本身失陷。
10. 信任模型：服务端失陷视同所有已登记设备失陷。服务端本来就能通过 MCP 配置等落点让设备执行命令，给客户端签名改变不了这一点，所以客户端不做签名，也不设发布密钥。服务端及其部署链路（GitHub 账户、CI 部署凭据）的安全由用户自行保证。
11. 发布与部署由 GitHub CI 在打 release tag 时完成：服务端和全部客户端从同一个 tag 构建，部署期间停服，不做无中断部署。
12. 服务器的 SSH（22 端口）对公网开放，CI 直接通过公网 SSH 部署，不引入 Tailscale、WireGuard 或 self-hosted runner。SSH 的安全通过只允许公钥登录和专用受限的部署账户来保证。
13. 代码仓库 `shichao402/Dec` 保持 GitHub 公开仓库（见需求 22）。公开不改变信任模型：安全仍以已定决策 10 为准，代码可见性既不是防线，也不承担保密职责。结论因此反过来——既然代码和提交历史任何人都能检索，密钥、真实公网地址、服务器地址和部署参数 SHALL NOT 出现在仓库里，一律走仓库外的配置（需求 22.2、22.4）。14. 本次是断代升级，新系统不兼容旧架构。官方资产与提供方机制、registry、`publish.firoyang.com`、`DecPersonalDevKit`、`dec-source-private` 全部废弃，不并入，也不作为上游。新系统建成、服务搭好之后，存量内容由 Agent 通过新系统的写入链路协助迁移（见需求 17），迁移完成后旧内容彻底删除。
15. 服务端域名为 `dec.firoyang.com`。TLS 证书由服务端通过 ACME 的 TLS-ALPN-01 方式自动向 Let's Encrypt 申请和续期，走的是 443 端口，因此不需要额外开放 80 端口。公网 443 由 nginx 持有，以 SNI 透传（不终止 TLS）方式转发到 dec-cloud 的回环高位端口 `127.0.0.1:8444`。
16. 管理面只做 Web，并且只通过本机代理访问。本期不做 Android 端，告警改走企业微信机器人和代理的系统通知（需求 12）。
17. 技术栈使用 Go：复用 `internal/secrets` 里的 Bitwarden API，以及现有渲染和 vars 模块中仍然适用的部分，其余按断代升级的原则重写。
18. SSH 远端机器一律作为“只接收设备”，各自安装代理。
19. 资产冷备和审计日志都放在 GitHub 私有仓库，与代码仓库分开。代码仓库公开而这两个仓库私有，只因为其中含加密后的真实资产和审计记录。账户是免费套餐：私有仓库用不了分支保护，用需求 15.2 的等效措施代替；公开仓库可以开启分支保护与 environment 保护规则，需求 21.7 因此改为直接启用它们。
20. 不做高危操作的跨设备确认，也不按项目划分写入范围。

## 需求

### 需求 1：云端服务作为唯一 SSOT

**用户故事：** 作为 Dec 的唯一用户，我希望资产、密钥、配置、设备登记和流程都以云端为唯一权威，这样就不会再有多副本漂移和跨系统对齐的问题。

#### 验收标准

1. 云端服务 SHALL 在内部 bare git 仓库里保存全部 Dec 资产和加密后的密钥，并且只能由服务自身提交。资产 SHALL NOT 再区分个人与官方，也 SHALL NOT 有 registry 或提供方上游（已定决策 14）。
2. 云端服务 SHALL NOT 对外暴露 git 协议、git 凭据，或任何能直接改写仓库的接口。
3. WHEN 资产或密钥修改成功 THEN 云端服务 SHALL 生成一次 commit，记录作者和来源设备，用于历史追溯和回滚。
4. 云端服务 SHALL 在 git 里保存服务配置和设备登记表（只存公钥和元数据）。
5. 服务端身份私钥 SHALL 用根密钥加密后存入 git，SHALL NOT 以明文出现在磁盘、git 或冷备中。
6. IF 用户要求把某项资产或密钥回滚到历史版本 THEN 云端服务 SHALL 用一次新的 commit 完成回滚，SHALL NOT 改写历史。

### 需求 2：超薄代理与固定能力白名单

**用户故事：** 作为用户，我希望每台机器上的代理只是一个下载即用的通用程序，配上服务地址就能工作，而且它能做的事有严格限制，云端出 bug 也不会写坏本机其他文件。

#### 验收标准

1. 代理 SHALL 只提供这几个固定原语：上报本机清单（OS、架构、用户目录、已安装 IDE 和 Agent 及其落点）、把指定内容写到白名单落点、删除云端指定且位于白名单内的文件、上报执行结果和状态、返回云端指定落点的文件哈希。
2. 代理 SHALL NOT 提供任意命令执行、任意路径读写或自我扩展能力。白名单落点 SHALL 内置在代理二进制里，云端 SHALL NOT 修改它。新增 IDE 或 Agent 落点时 SHALL 发布新版本代理，按需求 19 对齐。白名单的作用是防止云端缺陷误写，SHALL NOT 被视为防御服务端失陷的安全边界（见已定决策 10）。
3. WHEN 云端下发的写入目标不在白名单内 THEN 代理 SHALL 拒绝执行并上报。
4. 代理 SHALL 只主动向外连接云端，并保持一条长连接用于接收实时下发（需求 4.2），断开后按需求 5.4 重连。代理 SHALL NOT 监听任何公网入站端口，只在本机回环地址上提供本机页面、管理面转发和 MCP 入口。
5. 代理 SHALL 没有原生图形界面，交互只通过回环地址上的本机页面、CLI 和系统通知完成。代理以系统服务形式常驻（macOS 用 launchd，Windows 用服务或计划任务，Linux 用 systemd user service 加 linger）。
6. 代理与云端之间的协议 SHALL 带版本号。由于所有代理强制与服务端要求版本对齐（需求 19），云端 SHALL NOT 为多个代理版本维持兼容，只需保证版本握手方法永不改变（需求 19.7）。
7. 代理 SHALL NOT 自更新，版本由服务端统一规定、用户手动更新，流程见需求 19。
8. 代理 SHALL NOT 做签名校验，也 SHALL NOT 依赖安装脚本。用户从服务端下载通道（需求 20）下载二进制，下载后直接运行；首次运行时在本机页面或 CLI 里配置服务地址。公开仓库的 GitHub Release 只作备用下载路径，内容与服务端下载通道一致，但可能不是当前要求版本，以服务端下载通道为准。
9. 代理 SHALL 是通用二进制，SHALL NOT 内嵌任何服务地址、密钥或凭据。代理在本机只保存两样状态：服务地址，以及设备身份（设备私钥和设备证书）。服务器重建后不需要重新分发代理。
10. 回环入口 SHALL 只绑定 `127.0.0.1`，并且只做两项不增加使用摩擦的检查：Host 头必须是 `127.0.0.1:<端口>` 或 `localhost:<端口>`，用来防 DNS rebinding；请求如果带了 Origin 头，必须是代理自己的地址，否则拒绝，用来防其他网页跨站调用。系统 SHALL NOT 为回环入口设置会话 token、一次性链接或 CSRF token，MCP 入口也不需要 token。本机进程被视为可信，因为本机失陷就等于这台设备失陷。
11. 代理 SHALL 提供卸载命令：清理所有由 Dec 管理的落点和条目、删除本机设备身份，并在在线时通知云端注销这台设备。

### 需求 3：设备身份与安全通讯

**用户故事：** 作为用户，我希望每台设备都有独立身份，通过公网安全地连到云端，丢了一台设备可以单独吊销。

#### 验收标准

1. WHEN 新设备安装代理 THEN 代理 SHALL 在本机生成设备密钥对，私钥存进系统凭据库，不可用时退到权限为 0600 的文件。
2. 设备登记 SHALL 固定使用 Bitwarden 主密码 + 2FA 完成（需求 18.4）。设备类型（需求 18.2）由用户在新设备上登记时选择，验证通过后云端立即签发设备证书，不需要其他设备确认。
3. 代理与云端 SHALL 用 mTLS 双向认证：服务端用公共 CA 签发的证书证明身份，代理用服务端身份密钥签发的设备证书证明身份。服务地址 SHALL 由用户在首次运行时配置。修改服务地址等同于换了一个服务，代理 SHALL 清除原有设备身份并重新登记。
4. WHEN 用户吊销某台设备 THEN 云端 SHALL 立即拒绝该设备连接，并停止向它下发内容。
5. IF 服务重建后用同一份服务端身份私钥恢复 THEN 已登记设备 SHALL 无需重新登记即可自动重连。
6. 设备证书 SHALL 有有效期，并在到期前自动续签。续签只需要现有证书，不需要用户参与。有效期 SHALL 足够覆盖长期离线的设备（建议 1 年）。IF 证书已过期 THEN 代理 SHALL 提示用户按需求 18.4 重新登记。

### 需求 4：云端渲染与单向下发

**用户故事：** 作为用户，我希望资产和密钥一有变化，所有设备就自动收敛到最新状态，不需要我手动 pull。

#### 验收标准

1. 云端 SHALL 根据设备清单和该设备的订阅配置，在服务端完成资产渲染（包括变量和密钥替换），代理只负责落盘。
2. WHEN 资产或密钥 commit，或者设备订阅配置发生变化 THEN 云端 SHALL 立即对受影响的在线设备和落点重新渲染并推送，只下发内容哈希有变化的文件。
3. WHEN 设备上线 THEN 云端 SHALL 对比期望状态和设备上报的哈希，补齐差异。
4. 下发 SHALL 是幂等的。重复下发同样的内容 SHALL NOT 触发文件改写或 IDE 重载。
5. IF 渲染所需的密钥解密失败 THEN 云端 SHALL 保留设备上一次成功渲染的结果，并给出告警。SHALL NOT 用空值渲染。
6. 渲染出的明文密钥 SHALL 只出现在传输途中和最终落点，SHALL NOT 写进云端磁盘或 git。
7. 含明文密钥的落点文件 SHALL 以仅当前用户可读写的权限写入（类 Unix 上为 0600）。

### 需求 5：离线降级与本机缓存

**用户故事：** 作为用户，我希望云端宕机或网络断开时，各台机器上已有的配置照常可用。

#### 验收标准

1. WHILE 代理连不上云端 THEN 代理 SHALL 保持所有已落地文件不变，SHALL NOT 清理或回滚。
2. 代理 SHALL NOT 在本机保存下发状态清单。期望状态和下发记录只存在云端；对账时由云端告知要核对哪些落点，代理现场计算哈希并上报。
3. WHEN 重新连上云端 THEN 云端 SHALL 让代理上报所管理落点的当前哈希，并按需求 4.3 补齐。
4. 代理 SHALL 用指数退避重连，SHALL NOT 在断网期间高频请求。

### 需求 6：本地副本只读

**用户故事：** 作为用户，我希望本地落点只是云端的只读缓存，这样永远不会出现双向同步和冲突处理。

#### 验收标准

1. 本地落点 SHALL 视为只读缓存。系统 SHALL NOT 从本地文件回收任何改动，也 SHALL NOT 把本地改动转成提交。
2. IF 落点文件的哈希和最后一次下发的不一致 THEN 云端 SHALL 在下一次对账时直接用期望内容覆盖，并在管理面记一条“已覆盖本地改动”。在线期间，代理 SHALL 监听已管理落点的变化并立即上报哈希；监听不可用时，SHALL 退化为定期上报（例如每 10 分钟一次）。
3. IF 落点是 Dec 和 IDE 共用的配置文件（例如 MCP 配置）THEN 代理 SHALL 只覆盖 Dec 管理的条目，SHALL NOT 改动其他条目。这类文件的哈希 SHALL 只计算 Dec 管理的条目。
4. 系统 SHALL 在落点或其所在目录标注“由 Dec 管理，本地修改会被覆盖”，提示修改应走需求 7 或需求 8。

### 需求 7：资产的同步写入链路

**用户故事：** 作为用户或 Agent，我希望新增、修改、删除资产走一条独立的写入链路，发出请求后当场拿到结果，成功后所有设备马上生效。

#### 验收标准

1. 资产写入 SHALL 使用独立于读取下发的同步请求入口，由管理面和 Agent（MCP）共用。请求内容是按规定目录结构组织的 bundle 和 manifest（目标资产、操作类型、base revision）。
2. 客户端 SHALL 先在本地做格式和 schema 预校验，不通过就不发请求，并给出明确原因。
3. 云端 SHALL 在同一个请求内按固定流程依次执行：schema 校验、命名校验、密钥引用完整性校验（被引用的密钥必须存在）、疑似明文密钥扫描、提交 commit。任何一步失败 SHALL 使整个请求失败且不产生 commit，并返回失败的步骤和原因。
4. 写入语义 SHALL 是按 bundle 整体替换：提交后该 bundle 的内容与请求里给出的条目集合完全一致，未出现的旧条目会被删除。同一个请求重复执行 SHALL 结果一致。
5. 删除单个条目 SHALL 通过独立的删除请求表达，请求只包含 bundle 与条目路径。云端 SHALL 在事务内读出当前 manifest，仅移除路径匹配的条目及其名下文件，其余条目 SHALL NOT 受影响。IF 该路径在 manifest 中不存在 THEN 云端 SHALL 返回 not_found，SHALL NOT 静默成功。
6. IF 请求的 base revision 落后于当前 SSOT 版本 THEN 云端 SHALL 拒绝请求并返回最新 revision，SHALL NOT 静默覆盖。
7. 云端 SHALL 对资产和密钥写入共用一把锁、串行处理。
8. WHEN 请求成功 THEN 云端 SHALL 在响应里返回新的 revision，并立即按需求 4.2 下发到所有受影响的设备。

### 需求 8：Dec 自有的密钥管理

**用户故事：** 作为用户，我希望直接在 Dec 里配置密钥，看到它被哪些资产引用，并且密钥和资产处在同一个一致性范围内。

#### 验收标准

1. 系统 SHALL 在管理面提供密钥管理界面，支持新增、修改、删除，以及按平面和归属浏览。Agent SHALL 能通过 MCP 做同样的操作（明文查看除外，见需求 18.10）。
2. 密钥写入 SHALL 走同步请求，云端用当前根密钥按值加密后提交进 git，每条记录带 nonce 和 key id。
3. 界面 SHALL 展示每个密钥被哪些资产引用、被下发到哪些设备。
4. IF 要删除的密钥仍被资产引用 THEN 云端 SHALL 拒绝删除并列出引用它的资产，用户先修改或删除这些资产，再删除密钥。
5. 界面 SHALL 默认遮蔽密钥值，查看明文需要显式操作，并记入审计日志。
6. WHEN 密钥写入成功 THEN 云端 SHALL 立即触发受影响资产的重渲染和下发。

### 需求 9：根密钥存储与加载

**用户故事：** 作为用户，我希望服务重启后自动恢复全部能力，日常没有任何人工解锁步骤。

#### 验收标准

1. 根密钥 SHALL 是随机生成的 256 位密钥，以权限 0600、属主为服务账户的文件存放在服务器本地，路径 SHALL 位于 git 工作区之外。
2. 根密钥文件 SHALL NOT 进入 git、冷备或任何同步目录。
3. WHEN 服务启动 THEN 服务 SHALL 自动加载根密钥文件，并用 git 中的校验值验证。
4. IF 根密钥文件缺失或校验失败 THEN 服务 SHALL 以恢复模式启动：只开放健康检查（报告“恢复模式”）和恢复接口（需求 11），其余接口一律拒绝，并告警。服务 SHALL NOT 生成新的根密钥覆盖现有数据。
5. 系统 SHALL 支持根密钥轮换：生成新根密钥，重新加密当前所有密钥和服务端身份私钥，提交 commit，替换本地根密钥文件，并更新 Bitwarden 中的冷备副本。历史 commit 中的旧密文不重写。

### 需求 10：初始化与根密钥托管

**用户故事：** 作为用户，我希望首次部署时，在第一台设备的代理上一次完成根密钥生成、托管和本机登记，之后服务不再持有任何 Bitwarden 凭据。

#### 验收标准

1. 初始化 SHALL 经由代理完成：用户在第一台设备上安装代理并指向服务地址，代理发现服务未初始化后，在本机回环页面（或 CLI）展示初始化流程。服务 SHALL NOT 以 Web 页面形式向公网暴露初始化入口。初始化完成后，该入口 SHALL 永久关闭，发起初始化的这台设备 SHALL 同时登记为“我的设备”。
1a. 代理 SHALL 对用户配置的服务地址做标准 TLS 证书校验，服务端 SHALL 使用公共 CA 签发的证书（如 Let's Encrypt）。校验失败时代理 SHALL 拒绝连接，SHALL NOT 提供“忽略证书错误”选项，因为这是主密码和 2FA 不被中间人截获的前提。代理 SHALL NOT 采用首次信任（TOFU）。服务端身份密钥只用于签发和校验设备证书。
2. WHEN 用户在初始化界面提交 Bitwarden 主密码和 2FA THEN 服务 SHALL 生成根密钥并写入本地根密钥文件，再复用现有 Bitwarden API 实现登录，把根密钥按需求 10.6 的路径写入 Dec 专用账户作为冷备，然后读回比对，确认写入成功。
3. WHEN 冷备写入校验通过 THEN 服务 SHALL 登出 Bitwarden，并清除 access token、vault key 和主密码（主密码用字节数组接收，用完覆写）。服务 SHALL NOT 持久保存任何 Bitwarden 凭据。
4. IF 冷备写入或读回校验失败 THEN 服务 SHALL 中止初始化，SHALL NOT 进入已初始化状态。
5. 初始化 SHALL NOT 导入任何存量数据，初始化完成后服务是空的。存量资产和密钥按需求 17 由 Agent 协助迁移。
6. 根密钥冷备 SHALL 写在保留 folder `_dec-cloud` 下。folder 名以下划线开头，现有项目名规则（小写 kebab-case）不会产生这个名字，因此不会和项目 folder 冲突。条目名 SHALL 为 `root-key/<key-id>`，备注里 SHALL 写明“Dec Cloud 根密钥冷备，删除后服务器重建将无法恢复”，并附上 key id、创建时间和对应的服务实例标识。
7. 根密钥冷备 SHALL 只增不改：每次轮换都新建一个 `root-key/<新 key-id>` 条目，旧条目保留，不覆盖，以免一次误操作同时丢掉新旧两份。
8. 云端 SHALL NOT 在任何自动流程里删除或改写 `_dec-cloud` folder 中的条目。用户在迁移完成后清理旧 Bitwarden 条目时（需求 17.6），SHALL 保留这个 folder。

### 需求 11：恢复与重新托管

**用户故事：** 作为用户，我希望服务器重建或根密钥文件丢失时，能从 Bitwarden 取回根密钥，完整恢复服务。

#### 验收标准

1. 系统 SHALL 提供恢复流程，仅在恢复模式（需求 9.4）下可用，并且和初始化一样只经由代理的本机页面或 CLI 访问。由于此时服务无法验证设备证书，恢复请求 SHALL 走与需求 18.6 相同的受限接口与频率限制。
2. WHEN 用户在恢复界面提交 Bitwarden 主密码和 2FA THEN 服务 SHALL 根据 git 中记录的当前 key id，从 `_dec-cloud/root-key/<key-id>` 取回根密钥，用 git 中的校验值验证，通过后写回本地根密钥文件并正常启动，最后按需求 10.3 登出并清除凭据。
3. IF 取不到当前 key id 对应的条目，或者校验失败 THEN 服务 SHALL 拒绝恢复，并列出 `_dec-cloud` 下现有的条目供用户排查，SHALL NOT 用其他条目强行启动。
4. WHEN 根密钥轮换（需求 9.5）THEN 服务 SHALL 要求用户当场提供 Bitwarden 主密码和 2FA，新冷备条目写入并读回校验通过后，才切换到新根密钥。
5. 管理面 SHALL 显示根密钥冷备最后一次读回校验的时间。服务不持有 Bitwarden 凭据，所以无法自动巡检冷备，这个时间只在初始化、轮换和恢复时更新。
6. 服务器重建 SHALL 只需要冷备仓库和根密钥两样东西，即可恢复资产、密钥、设备登记和服务端身份。重建流程 SHALL 是：声明式部署（需求 16.1）→ 从冷备平台克隆仓库（克隆凭据由用户在重建时手动提供，用后删除）→ 服务进入恢复模式 → 按本需求取回根密钥。

### 需求 12：告警

**用户故事：** 作为用户，我希望 Dec 出问题时能及时收到通知，不用自己去看管理面。

#### 验收标准

1. 云端 SHALL 通过两条通道发出告警：企业微信群机器人 webhook，以及所有在线的“我的设备”上代理的系统通知。webhook 地址 SHALL 作为 Dec 密钥存储。
2. 以下事件 SHALL 触发告警：服务进入恢复模式、设备登记尝试（无论成功还是失败）、冷备或审计推送失败、冷备远端历史被改写（需求 15.2）、渲染时密钥解密失败（需求 4.5）、部署失败或回滚。
3. 云端整体不可用时，云端无法自己告警。因此代理 SHALL 在与云端断连超过阈值（默认 30 分钟）时发出本机系统通知。CI 部署失败由 GitHub 自带的 workflow 失败通知兜底。
4. 同一类告警在短时间内 SHALL 合并发送，避免刷屏。

### 需求 13：Agent 接入

**用户故事：** 作为在各台机器上使用 Agent 的用户，我希望 Agent 仍能查询和修改 Dec 资产与密钥，但只能走收敛后的入口。

#### 验收标准

1. 系统 SHALL 为本机 Agent 提供 MCP 入口。该入口 SHALL 由代理在本机回环地址上暴露，经设备身份转发到云端，SHALL NOT 把云端 MCP 直接暴露到公网。
2. Agent 可用的写操作 SHALL 仅限需求 7 的资产写入和需求 8 的密钥写入，SHALL NOT 提供任何通过修改本地文件影响 SSOT 的工具。
3. 现有的 `dec_push` 等双向同步类工具 SHALL 下线。

### 需求 14：管理面

**用户故事：** 作为用户，我希望在一个地方看到所有设备、资产、密钥的状态，并完成全部管理操作。

#### 验收标准

1. 云端 SHALL 提供管理面，内容包括：设备列表和在线状态、每台设备与期望状态的差异、资产浏览与写入、资产与密钥的历史和回滚、密钥管理、本地改动覆盖记录。
2. 管理面 SHALL 只对“我的设备”开放，SHALL NOT 在公网暴露任何 Web 页面。浏览器 SHALL 通过本机代理在回环地址上暴露的入口访问管理面，由代理用设备身份转发，浏览器本身不需要安装客户端证书。初始化、根密钥恢复和设备登记也都经由代理完成（需求 10、11、18.4）。
3. 管理面上的所有写操作 SHALL 记入审计日志。

### 需求 15：审计与冷备

**用户故事：** 作为用户，我希望服务器损坏或被攻破后，我能知道发生了什么，并且能完整恢复。

#### 验收标准

1. WHEN 仓库产生新 commit THEN 云端 SHALL 异步推送到冷备仓库 `shichao402/dec-cloud-backup`（GitHub 私有仓库），并每天定时补推一次兜底。部署期间（需求 21.2）SHALL 暂停推送，直到健康检查通过后再恢复，以免把之后可能被回滚的数据迁移 commit 推到冷备。
2. 冷备和审计仓库是私有仓库，免费套餐下私有仓库无法开启分支保护，因此改用以下等效措施：推送凭据 SHALL 是只绑定这一个仓库的 deploy key；云端 SHALL NOT force-push；每次推送前，云端 SHALL 先 fetch 远端，并确认远端 head 是本地历史的祖先。IF 远端历史被改写 THEN 云端 SHALL 停止推送并告警，SHALL NOT 用本地历史覆盖远端，由用户判断原因后再处理。这条限制只作用于这两个私有仓库，不涉及已公开的代码仓库。
3. 审计日志（资产写入、密钥写入与明文查看、下发、设备登记与吊销、根密钥加载与轮换、初始化与恢复、部署）SHALL 以只追加的方式推送到独立私有仓库 `shichao402/dec-cloud-audit`，使用该仓库专用的 deploy key，并遵守与 15.2 相同的推送规则。已知的局限是：如果服务器失陷，攻击者可以用这把 deploy key 改写审计仓库，此时 GitHub 仓库 Activity 中留下的 force-push 记录是剩下的取证线索。
4. 冷备或审计推送失败时 SHALL 告警（需求 12）。

### 需求 16：云端运维基线

**用户故事：** 作为唯一的运维者，我希望日常维护成本尽量低，并且部署可以重复执行。

#### 验收标准

1. 云端部署 SHALL 采用声明式方式（例如 docker compose 或 Nix），一条命令即可从零重建。日常版本更新 SHALL 由需求 21 的 CI 部署完成。
2. 云端 SHALL 开启操作系统自动安全更新。
3. 公网 SHALL 只开放两个端口：HTTPS（客户端证书可选）和 SSH（22）。HTTPS 端口上无需设备证书即可访问的端点 SHALL 仅限三个：设备登记（需求 18.6，根密钥恢复复用它）、客户端下载（需求 20）、健康检查（需求 16.4）。其余接口一律要求设备证书。
3a. SSH SHALL 只允许公钥登录，禁用密码登录和 root 直接登录，并启用 fail2ban 或同等的暴力破解防护。登录用户分为两类：用户本人的运维账户，以及 CI 专用的部署账户（需求 21.6）。
4. 云端 SHALL 提供健康检查，供代理和外部探活检测可用性。
5. 根密钥文件 SHALL 放在不参与云厂商磁盘快照或镜像备份的位置，或者确认这些快照不会离开自己的账户。

### 需求 17：断代切换与存量迁移

**用户故事：** 作为现有 Dec 用户，我希望新系统不背旧架构的包袱；新系统建好以后，让 Agent 帮我把存量资产和密钥搬进去，搬完再把旧的东西彻底删掉。

#### 验收标准

1. 新系统 SHALL NOT 兼容旧架构的数据格式、协议或工具，也 SHALL NOT 内置专门的导入工具。
2. 迁移 SHALL 在服务搭建完毕、至少一台“我的设备”登记完成之后进行。由本机 Agent 读取旧内容（`DecPersonalDevKit`、`dec-source-private` 的本地克隆，以及旧系统落在本机的资产和密钥文件），按新系统的格式整理后，通过 MCP 调用需求 7 和需求 8 的写入链路逐项写入。迁移写入 SHALL 和日常写入一样经过全部校验，不设旁路。
3. 迁移写入 SHALL 在 commit 中记录来源（原仓库、原路径），方便追溯。
4. 迁移密钥时，Agent SHALL 直接读取旧密钥文件，通过需求 8 的常规密钥写入链路提交，不设专用工具。明文会经过 Agent 的上下文，这是一次性迁移，用户已接受。代理 SHALL NOT 为此新增任何本地读取能力（与需求 2.2 一致）。
5. 新旧系统 SHALL NOT 在同一台设备上并存。每台设备切换时，SHALL 先卸载旧版 Console、`dec-server`、`dec-mcp`，并清理它们渲染出的落点，再安装新代理。切换顺序 SHALL 是：搭建服务 → 登记第一台设备 → 迁移 → 在第一台设备上验证 → 逐台切换其余设备。
6. WHEN 用户确认迁移完成 THEN 用户 SHALL 删除旧内容，系统 SHALL NOT 自动删除。要删除的旧内容包括：`DecPersonalDevKit` 和 `dec-source-private` 仓库、registry、`publish.firoyang.com`、旧的公开 Release 和安装脚本，以及 Bitwarden 中旧的 Dec 密钥条目（`_dec-cloud` folder 除外，见需求 10.8）。
7. 迁移 SHALL NOT 阻塞新系统的开发和上线。新系统在空数据状态下就应完整可用。

### 需求 18：访问主体与权限

**用户故事：** 作为唯一用户，我希望不用理解角色和管理员这类概念，只记住一条规则：我的设备都能管理 Dec；设备全丢了，就用 Bitwarden 主密码和 2FA 证明我是我。

#### 验收标准

1. 系统 SHALL 只有一个人类用户（owner），SHALL NOT 提供账户注册、口令登录或多用户能力。所有访问主体都是已登记设备，身份就是设备证书。
2. 设备 SHALL 只有两种类型：
   - 我的设备（默认）：拥有全部能力，包括写入、管理面、设备登记与吊销、回滚、查看明文、根密钥轮换。
   - 只接收设备：只接收下发，不能写入，也不能使用管理面。适用于服务器、SSH 远端这类无人看管的机器。
   类型 SHALL 在登记确认时选择，之后可随时修改，并立即生效。
3. 所有权证明 SHALL 统一为 Bitwarden 主密码 + 2FA，与初始化、根密钥恢复使用同一套凭据，用户不需要额外保管任何恢复码、登记码或服务器登录方式。
4. 新设备登记 SHALL 只有一条路径：在新设备的代理上输入 Bitwarden 主密码和 2FA。有浏览器的设备通过代理的本机回环页面输入，无桌面设备通过代理 CLI 在终端输入。系统 SHALL NOT 提供登记码等其他登记方式。
5. WHEN 代理提交登记请求 THEN 云端 SHALL 复用现有 Bitwarden API 登录，读取 `_dec-cloud/root-key/<当前 key-id>`，与本地根密钥比对一致后，才签发设备证书，随后按需求 10.3 登出并清除凭据。主密码和 2FA SHALL 只经代理与云端之间的加密通道传输，SHALL NOT 落盘。
6. 登记接口 SHALL 只存在于代理协议内（无证书端点之一，见需求 16.3），SHALL NOT 以 Web 页面形式暴露到公网。该接口 SHALL 有失败次数限制和冷却时间，每次尝试 SHALL 记入审计日志并告警到所有“我的设备”。
7. 设备丢失时，用户 SHALL 能在任意一台其他“我的设备”上吊销它。IF 手上已没有其他设备 THEN 用户 SHALL 在新设备上按需求 18.4 登记，再吊销丢失的设备。系统 SHALL NOT 要求用户登录服务器。
8. 吊销 SHALL 只在服务端生效，SHALL NOT 依赖丢失的设备在线配合。WHEN 设备被吊销 THEN 云端 SHALL 列出曾经渲染到该设备上的全部密钥，作为轮换清单在管理面跟踪，直到全部处理完。
9. 设备 SHALL 只能拿到自己订阅范围内的渲染结果。云端 SHALL NOT 提供“列出或读取全部密钥值”的接口。
10. Agent 经 MCP 入口访问时 SHALL 自动受限，用户无需配置：可以读写资产和密钥、查看密钥元数据；SHALL NOT 查看明文、管理设备、回滚或轮换根密钥。这一限制只用于防止 Agent 误操作，SHALL NOT 被视为安全边界。
11. 高危操作（吊销设备、删除密钥、回滚、根密钥轮换、查看明文）SHALL 在界面上二次确认，并记入审计日志。审计日志 SHALL 写明设备 ID 和来源入口。
12. 服务器本机 SHALL 保留管理命令（吊销设备、为指定设备公钥直接签发证书），仅作为 Bitwarden 也不可用时的最后手段，不出现在日常流程和界面引导里。

### 需求 19：客户端版本由服务端统一控制

**用户故事：** 作为用户，我希望所有客户端的版本由服务端统一规定，不对齐的设备会被明确拦住并提示我去更新，这样我不用记每台机器装的是什么版本。

#### 验收标准

1. 服务端 SHALL 是客户端版本的唯一权威。要求的客户端版本 SHALL 由每次发布的发布清单声明，随服务端部署（需求 21）一起生效，SHALL NOT 另外手动配置。所有代理 SHALL 与该版本对齐。
2. 发布清单中的要求版本 SHALL 默认等于本次发布版本。IF 本次发布没有改动客户端 THEN 发布清单 MAY 沿用上一个要求版本，避免只修服务端时也要求所有设备更新。IF 本次发布对代理协议做了不兼容变更 THEN 要求版本 SHALL 提升，CI SHALL 校验这一点：协议版本变化但要求版本没变时，构建失败。
3. 代理 SHALL NOT 自动更新。更新方式固定为：用户从服务端下载通道（需求 20）下载要求版本，替换后重启代理。
4. WHEN 代理连接云端 THEN 代理 SHALL 上报自身版本。IF 版本与要求版本不一致 THEN 云端 SHALL 拒绝该设备除“上报版本”和“获取要求版本”之外的所有请求，SHALL NOT 继续向它下发内容。
5. WHILE 代理处于版本不对齐状态 THEN 代理 SHALL 保持已落地文件不变（与需求 5.1 一致），并在本机页面、CLI 和系统通知中提示“需要更新到版本 X”，附服务端下载通道中该版本的地址。
6. 管理面 SHALL 显示要求版本、每台设备的当前版本，以及未对齐的设备列表。
7. “上报版本”和“获取要求版本”两个方法 SHALL 是协议中永不破坏兼容的部分，任何版本的代理都必须能调用它们，以保证旧代理总能收到更新提示。
8. 落点白名单 SHALL 随代理二进制发布（需求 2.2），新增落点等同于发布新版本，同样走本需求的对齐流程。

### 需求 20：客户端下载通道

**用户故事：** 作为用户，我希望服务端提示我更新时，直接从服务端就能下载到要求的版本，不用再去 GitHub 找对应的版本和平台。

#### 验收标准

1. 服务端 SHALL 在公网 HTTPS 端口上提供只读、无需设备证书的下载端点，提供当前要求版本的客户端二进制（按 OS 和架构区分）和一个简单的下载索引页。
2. 客户端二进制 SHALL 由 CI 在部署时一并上传（需求 21.2），服务端 SHALL NOT 主动从外部拉取。
3. 下载内容 SHALL 只包含通用二进制（需求 2.9），SHALL NOT 包含任何配置、凭据或设备信息。
4. 下载端点 SHALL 有频率限制，访问记入审计日志，但 SHALL NOT 为此告警。
5. 服务端 SHALL 保留上一个要求版本的二进制，供部署回滚（需求 21.3）使用。更早的版本 SHALL 删除，需要时从 GitHub Release 获取。
6. macOS 和 Windows 的二进制不签名。下载索引页 SHALL 给出命令行下载方式（例如 `curl`，避开浏览器给文件打上的 quarantine 标记），以及在 Gatekeeper 或 SmartScreen 拦截时放行的说明。

### 需求 21：发布与部署

**用户故事：** 作为用户，我希望打一个 release tag 就能完成服务端和客户端的发布和部署，部署时短暂停服，失败自动回到上一个版本。

#### 验收标准

1. WHEN 推送 release tag THEN GitHub CI SHALL 从该 tag 构建服务端和全部客户端，生成 GitHub Release（含发布清单和全部二进制），然后执行部署。所有平台的二进制 SHALL 在 Linux runner 上用 Go 交叉编译，SHALL NOT 使用 macOS 或 Windows runner。唯一例外是托盘（链接 AppKit，Linux 上无 macOS SDK），它允许使用 macOS runner，且该 runner SHALL 只用于构建托盘。代码仓库是公开仓库，Actions 分钟数不受私有仓库额度限制，但仍 SHALL 控制用量：macOS runner 按 10 倍分钟计费且排队更久，不得用于 Linux 可完成的工作。
2. 部署 SHALL 按固定顺序执行：服务进入维护状态并停服 → 快照当前服务端版本、客户端二进制和数据 → 上传新服务端和新客户端二进制 → 启动（包括必要的数据迁移）→ 健康检查 → 退出维护状态。
3. IF 任何一步失败或健康检查不通过 THEN 部署 SHALL 回滚到快照中的服务端版本、客户端二进制、要求版本和数据，并告警。
4. WHILE 服务处于维护状态 THEN 代理 SHALL 按需求 5 离线降级。重连后，云端 SHALL 按需求 19.4 判断版本是否对齐。
5. 部署 SHALL NOT 改动根密钥文件。git 数据和设备登记表只允许由启动时的数据迁移修改，并且 SHALL 包含在步骤 2 的快照里。
6. CI SHALL 通过公网 SSH 连接服务器，使用专用部署账户和专用密钥，不复用用户本人的运维密钥。部署账户 SHALL 只拥有部署所需的权限：写入发布目录、执行部署脚本、重启 Dec 服务，SHALL NOT 拥有通用 sudo 权限。部署账户的 SSH 公钥 SHALL 在 `authorized_keys` 中用 `command=` 限定只能执行部署入口脚本。服务器的 SSH host key 指纹 SHALL 预先写入 CI 的 known_hosts，CI SHALL NOT 自动接受未知的 host key。
7. 部署凭据 SHALL 是专用的部署身份，存放在 Actions environment secret 中，SHALL NOT 存为仓库级 secret。代码仓库是公开仓库，因此 SHALL 启用 environment 保护规则来限制这个 secret 的使用范围：部署 SHALL 只允许在 `refs/tags/v*` 上引用该 environment。此外，部署入口脚本 SHALL 校验上传的发布清单中的 tag 和 commit 与 GitHub 上真实存在的 release tag 一致；仓库 SHALL NOT 添加其他协作者，也 SHALL NOT 启用会运行外部 PR 代码的触发器。由于部署会替换服务端二进制，部署凭据实际上等同于服务器的完全控制权，因此 GitHub 账户 SHALL 开启 2FA，这是已定决策 10 中“用户自行保证安全”的一部分。
8. 每次部署 SHALL 记入审计日志，内容包括版本、tag、commit、结果和是否回滚。

### 需求 22：代码仓库公开与信息公开边界

**用户故事：** 作为作者，我希望重构后的 Dec 代码保持公开，可以被检索和审阅；同时，正因为代码和提交历史人人可见，密钥、真实服务器地址和部署参数都不能出现在仓库里。

#### 验收标准

1. Dec 的代码仓库 `shichao402/Dec`（服务端、代理、CI 配置）SHALL 保持 GitHub 公开仓库。冷备仓库 `dec-cloud-backup` 和审计仓库 `dec-cloud-audit`（需求 15）SHALL 保持私有，并且与代码仓库分开：这两个仓库装的是加密后的真实资产和审计记录，属于运行数据，不是代码。`DecPersonalDevKit` 和 `dec-source-private` SHALL NOT 在新系统中继续使用，迁移完成后按需求 17.6 删除。
2. 由于提交历史对所有人可检索，仓库中 SHALL NOT 出现任何真实凭据（根密钥、deploy key、Actions secret、Bitwarden 凭据、webhook 地址）、真实公网 IP 或服务器登录信息。这些一律通过 GitHub Actions secret、服务器本地文件和仓库外的配置提供。CI 日志 SHALL NOT 回显出这些值。
3. 公开之前，SHALL 对现有历史做一次泄露排查：扫描历史 commit 中的密钥、内部域名、服务器地址等敏感信息。排查出的密钥 SHALL 一律视为已泄露并轮换，SHALL NOT 依赖改写历史来补救，因为公开期间的历史可能已被 fork 或克隆。
4. 历史中已经存在的服务端域名 `dec.firoyang.com` 与回环地址（`127.0.0.1`、`0.0.0.0`）不构成泄露，允许保留在代码和文档中：域名本身是公开信息（证书透明日志里可查），回环地址不指向任何真实主机。但真实公网 IP、SSH 端口转发细节、服务器上的绝对路径和账户名 SHALL NOT 写入仓库。
5. 现有面向公开用户的发布物，包括公开 Release、安装脚本、对外文档、registry 和 `publish.firoyang.com`，SHALL 按需求 17.6 彻底删除，不保留归档。公开仓库的 GitHub Release SHALL 只发布二进制和发布清单，SHALL NOT 附带任何环境配置。
6. 公开仓库 SHALL 开启 GitHub 免费套餐在公开仓库下可用的两项原生保护：`main` 分支保护与部署用的 environment 保护规则（需求 21.7）。分支保护的范围 SHALL 是最小必要的一组，只禁止强制推送和删除分支，SHALL NOT 要求 PR 评审、SHALL NOT 要求状态检查，因此单人直接推 `main` 的日常流程不受影响。分支保护 SHALL 覆盖管理员（`enforce_admins=true`）：GitHub 默认把管理员排除在保护之外，不打开这一项等于没开。开启后强推已被禁止，但改写历史仍 SHALL NOT 被当作凭据泄漏的补救手段（第 3 条），因为公开期间的历史可能已被 fork 或克隆，阻塞强推只能防止「以后被覆盖」，不能收回「已经流出去的内容」。
7. 公开仓库 SHALL NOT 接受会执行外部 PR 代码的触发器。`pull_request_target` 和带写权限的 `workflow_run` SHALL NOT 用于任何持有 secret 的 job。仓库 SHALL NOT 添加其他协作者。
8. 公开不改变信任模型（已定决策 10、13）：代码可见性 SHALL NOT 被当作安全边界，SHALL NOT 因此放松任何鉴权、加密或审计要求。服务端、部署链路和 GitHub 账户的安全由用户自行保证。

### 需求 23：资产模型与订阅

**用户故事：** 作为用户，我希望明确知道资产有哪些类型、落到哪里，以及每台设备、每个项目分别拿到哪些资产。

#### 验收标准

1. 资产 SHALL 按 bundle 组织，一个 bundle 对应一个业务或产品分组（例如 `woa`、`tencent-cloud`）。资产类型 SHALL 为：skill（目录型，子目录随整体下发）、rule、MCP 条目、env 文件（由密钥渲染得到）。资产内容 SHALL 支持变量替换和密钥引用。
2. 落点 SHALL 分为两个平面：用户平面落在用户目录下各 IDE 和 Agent 的全局位置；项目平面落在某个项目根目录下的 IDE 和 Agent 目录。
3. 订阅 SHALL 分两级配置，都存放在云端的设备配置里：设备的用户平面订阅了哪些 bundle；设备上登记了哪些项目，每个项目订阅了哪些 bundle。项目登记的内容是“设备、本机绝对路径、订阅的 bundle”，可以在管理面或代理 CLI 中完成。
4. 代理白名单（需求 2.2）对项目平面的规则是：已登记的项目根目录，加上内置的 IDE 相对目录模式（例如 `.cursor/`、`.codebuddy/`）。项目根目录 SHALL 位于用户目录之下，并且必须已经存在。代理不会自动发现或创建项目。
5. IF 两个 bundle 会渲染出同一个落点上的同名托管条目 THEN 云端 SHALL 在写入或订阅变更时拒绝并指出冲突，SHALL NOT 让后渲染的一方静默覆盖前一方。
6. 共享配置文件中由 Dec 管理的条目 SHALL 使用统一前缀命名（例如 `dec-<名称>`），并且只按这个前缀识别和清理（需求 6.3）。

## 实施约定

1. Agent SHALL 自行完成可自动化的外部操作：用 gh（本机已登录 `shichao402`）创建仓库、设置可见性、配置 Actions secret 和 workflow、发布 release；用本机的 `dec-tencent-cloud` MCP 处理腾讯云资源，包括云服务器、DNSPod 上 `dec.firoyang.com` 的解析和安全组（只开放 22 和 443）。
2. `dec-tencent-cloud` 是旧 Dec 渲染出来的资产。在迁移完成之前，它 SHALL 保持可用；迁移时把它迁入新系统，在新系统验证可用之后，才删除旧版本。
3. 需要用户本人参与的步骤只有输入 Bitwarden 主密码和 2FA 的环节：首次部署完成后的初始化（需求 10），以及之后每台新设备的登记（需求 18.4）。到这些步骤时，Agent SHALL 暂停并通知用户，用户完成后再继续。
4. 删除类操作（旧仓库、registry、`publish.firoyang.com`、Bitwarden 旧条目）SHALL 由用户执行，或者逐项确认后再执行（需求 17.6）。
